# 성능 개선 가설 평가 및 실무 적용 방안

> **작성 기준:** 2026-05-09  
> **관련 연구:** 서울시 공구대여 데이터 공구명 표준화 — RAG v2 Improved  
> **현재 최고 성능:** gemma4:e4b 88.47% (GT 457건 기준)

---

## 1. 가설: "누수 없는 88.5% → 프롬프트·데이터 보완으로 더 높아질 수 있다"

### 1.1 전제 점검 — "누수 없음"이 실제로 의미하는 것

RAG 시스템의 구조적 특성상 다음을 명확히 구분해야 한다.

```
검색 corpus = 표준명 리스트 (예: ["드릴", "망치", "렌치", ...])
GT            = (원본명, 표준명) 쌍 457개

→ GT의 정답(표준명)은 반드시 retrieval corpus에 존재한다.
   그렇지 않으면 정확도가 0%에 가까워지기 때문.
```

엄밀히 말하면 이것은 **설계상의 retrieval leakage**다. 정답이 후보 풀에 포함되어 있다는 조건이 보장된 평가다. "데이터 누수 없음"은 맞지만, **"정답이 k=15 후보 안에 항상 들어온다"는 더 강한 가정**이 성립할 때만 현재 정확도가 의미 있다.

> 이 가정이 GT 457건 외의 2,895건에도 성립하는지 검증된 바 없다.

---

## 2. 세 가지 개선 방향별 평가

### 2.1 더 나은 프롬프트 → 기대치: +2~4%

| 구분 | 이유 |
|------|------|
| 효과 있는 경우 | LLM이 후보 중 올바른 표준명을 골랐으나 프롬프트 지시가 애매해서 틀린 경우 |
| 효과 없는 경우 | 올바른 표준명이 k=15 후보에 없었던 경우 (retrieval failure) |
| 구조적 한계 | fallback 메커니즘: LLM 출력이 후보 외 → rag_top1 강제 적용. 프롬프트로 해결 불가 |

일본어 잔재(47.1%)의 오답 9건은 "기리"→"드릴" 연결을 BGE-m3-ko가 retrieval 단계에서 실패했을 가능성이 높다. 프롬프트 개선으로는 해결되지 않는다.

**결론: 프롬프트 최적화의 천장은 낮다. 이미 88.5%까지 온 시스템에서 프롬프트로 추가 +5% 이상 달성하기는 어렵다.**

---

### 2.2 더 많은 표준이름 데이터 → 조건부 효과, 단순 확대는 역효과 가능성

"표준이름 데이터"가 무엇을 의미하느냐에 따라 완전히 다른 결과가 나온다.

| 의미 | 효과 | 이유 |
|------|------|------|
| GT 457건 → 더 많은 (원본, 표준명) 주석 쌍 | 평가 범위 확대 but 정확도 향상 아님 | GT는 평가에 쓰임. 더 많이 주석해도 RAG retrieval은 개선 안 됨 |
| 표준명 리스트 확대 (corpus 추가) | 이미 없는 표준명이 있을 때만 효과 | 현재 457건의 정답은 이미 corpus에 있음. 신규 공구 유형 추가 시 유효 |
| 동의어/별칭 사전 추가 | **핵심 개선 포인트** | 기리→드릴, 뺀치→펜치 등 연결 고리 부재가 근본 문제 |

**중요 오해**: 주석 데이터를 더 쌓으면 모델이 똑똑해진다는 가정. 이 시스템은 LLM을 fine-tune하지 않는다. LLM 가중치는 고정이다. GT 주석 확대 → RAG retrieval 품질 향상으로 직접 연결되지 않는다.

---

### 2.3 더 많은 참고자료 보완 → 가장 ROI 높음, 단 종류가 중요

| 참고자료 종류 | 예상 효과 | 구체 수치 |
|------|------|------|
| 일본어 공구용어 사전 (기리→드릴 등) | **가장 높음** | 일본어 잔재 47.1%→80%+ 예상, 전체 +1.5~2% |
| 카테고리별 공구 설명서 | 중간 | 기타(66.7%) 개선 기여 |
| 브랜드-제품명 대응 목록 | 중간 | 브랜드 혼입(87.5%) → 90%+ |
| 영문 약어 전개 사전 | 낮음 | 영문/약어(82.5%) → 85%+ (이미 충분히 높음) |

## 3. 달성 가능한 정확도의 현실적 천장

현재 아키텍처(RAG + 소형 LLM) 기준:

```
현재:          88.5% (GT 457건 기준)
단기 개선 후:  ~92~94% (일본어 사전 + 프롬프트 + corpus 보완)
구조적 천장:   ~95% 내외

나머지 5%:
  - 진짜 모호한 공구명 (망치 → 목공망치 vs 일반망치 구분 불가)
  - 2개 이상의 유효 표준명이 존재하는 케이스
  - 현장 맥락 없이는 판단 불가능한 케이스
  → 이 5%는 LLM으로 해결 불가. 사람 검토 필요.
```

**중요 경고**: 현재 88.5%는 GT 457건(전체 3,352건의 13.6%) 기준이다. 나머지 86.4%의 실제 정확도는 측정된 바 없다. 전체 3,352건의 진짜 정확도는 80~85% 수준일 가능성이 있다.

## 4. 실제 업무 개선 적용 방안

### Phase 1: 즉시 적용 가능 (1~2주)

**① 일본어 공구용어 전처리 사전 구축**

```python
JAPANESE_MAP = {
    '기리': '드릴',
    '뺀치': '펜치',
    '빤치': '펜치',
    '빠루': '노루발장도리',
    '오함마': '대형해머',
    '겐나와': '대형해머',
    '구루마': '손수레',
    '니빠': '니퍼',
}
# RAG 호출 전 선처리 → 일본어 잔재 47.1% → 80%+ 예상
```

50~100개 항목, 하루 작업 분량.

**② 인코딩 오류·운영용 텍스트 사전 필터링**

```python
# LLM 호출 전 사전 탈락 처리
if '?' in name or '▯' in name:
    skip → "인코딩 오류 — 수동 처리 필요"
if any(k in name for k in ['원)','문의','예약']):
    skip → "운영 텍스트 — 무시"
```

이 두 유형은 LLM에 넣을 대상이 아니다.

---

### Phase 2: 신뢰도 기반 반자동화 (1~2개월)

```
신뢰도 측정 방법: rag_top1 score vs rag_top2 score의 격차
  → 격차 크면 (≥0.3) 고신뢰, 격차 작으면 저신뢰

고신뢰 (~60% of items) → 자동 적용
중간   (~25%)           → 담당자 1차 검토 (1-click 승인)
저신뢰 (~15%)           → 완전 수동 처리
```

예상 효과: 전체 수작업 공수의 60~75% 절감.

---

### Phase 3: 피드백 루프 구축 (3~6개월)

```
현장 담당자 수정 → 오류 케이스 축적 → GT 자동 확장
                                      → Retrieval corpus 보완
                                      → 다음 배치에서 동일 오류 자동 교정
```

6개월 후 예상: GT 457건 → 1,500~2,000건 수준으로 자연 성장. 전체 정확도 +5~8% 기대.

---

### 4.1 배포 권장 모델 — 유형별 라우팅 검토

| 유형 | 최고 성능 모델 | 정확도 |
|------|------|------|
| 세트/구성품 | exaone3.5:7.8b | 96.2% |
| 오탈자 | gemma4:e4b / granite4.1:8b | 93.8% / 93.1% |
| 메타데이터 | gemma4:e4b / granite4.1:8b / exaone3.5:7.8b | 90%+ |
| 일본어 잔재 | gemma3:4b (단, 선처리 후) | 52.9% |
| 전체 | gemma4:e4b | 88.5% |

배치 처리 환경이라면 유형별 전문 모델 라우팅 → 전체 +2~3% 추가 가능.

## 5. 종합 판단

| 항목 | 평가 |
|------|------|
| 가설의 방향성 | **맞음** — 개선 여지는 실존 |
| 프롬프트 개선 단독 | 기대 이하. 천장 낮음 (+2~4%) |
| 표준명 데이터 단순 확대 | 효과 없음. **동의어 사전 추가**가 핵심 |
| 참고자료 보완 | **가장 ROI 높음** — 일본어 사전이 즉각적 효과 |
| 현실적 달성 가능 정확도 | GT 기준 ~92~95%, 전체 3,352건 기준 ~86~90% |
| 완전 자동화 가능성 | **불가** — 5~15%는 구조적으로 사람 검토 필요 |
| 실무 적용 최우선 과제 | 일본어 선처리 사전 + 신뢰도 기반 반자동화 |
