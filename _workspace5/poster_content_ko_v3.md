# 포스터 내용 (국문) v3 — LLM+RAG 기반 비정형 공구 이름 표준화

> 대상: 국내 학술대회 (AI·데이터·정보처리 분야)
> 구성: 초록 / 서론 / 연구 방법 / 실험 결과 / 결론
> 기반: 전문석사 프렉티컴보고서(RAG v1) + RAG v2 개선 실험 결과 + 더티데이터 유형별 분석 + LLM-only 비교 실험

---

## 제목

**로컬 LLM과 검색 증강 생성(RAG)을 활용한 비정형 범주형 데이터의 의미론적 표준화**
— 산업용 공구 이름 데이터를 중심으로

*(단축 제목 후보: "오픈소스 LLM·RAG 기반 공구 이름 더티데이터 의미론적 표준화 실험")*

---

## 초록

> *(약 200자 — 포스터 초록란 기준)*

수동 입력으로 생성된 비정형 범주형 데이터는 어휘적 다양성으로 인해 데이터 품질 저하 및 머신러닝 성능 감소를 유발한다. 본 연구는 오픈소스 거대 언어모델(LLM)과 검색 증강 생성(RAG)을 결합한 의미론적 표준화 파이프라인을 제안한다. 서울시 공구대여 데이터(3,352개 고유 공구명, 160종 표준명)를 대상으로 12개 오픈소스 LLM을 두 가지 RAG 구성으로 평가하였다. 기본(Baseline) RAG는 약 55%의 정확도를 보인 반면, 한국어 특화 임베딩(BGE-m3-ko), BM25+FAISS 하이브리드 검색, 후보 확대(k=15), 카테고리 주입을 적용한 개선(Improved) RAG는 최고 **88.47%**의 정확도를 달성하였다(+33.3%p). LLM-only 대비 RAG 기여도 +61pp 이상 확인: RAG 없이 LLM 단독으로는 9~27%에 불과하여 실용 수준에 미달함을 정량적으로 규명하였다. 더티데이터 유형별 분석 결과, 오탈자(33.9%, 93.8%)·동력원 명시(96.4%) 등은 높은 정확도를 보인 반면, 일본어 잔재 용어(47.1%)는 임베딩·어휘 검색 모두에서 구조적 실패가 확인되었다. 모델 크기보다 도메인 특화 검색 아키텍처가 성능에 더 큰 영향을 미침을 실험적으로 확인하였다.

**주요어:** 비정형 데이터, 데이터 표준화, 거대 언어모델, 검색 증강 생성, 데이터 품질

## 1. 서론

### 1.1 연구 배경

| 항목             | 수치         |
| -------------- | ---------- |
| 서울시 공구대여 전체 기록 | 11,525건    |
| 고유 공구 이름 문자열   | **3,352개** |
| 실제 공구 표준 종류    | **약 160종** |
| 1종당 평균 표기 변형 수 | **~21가지**  |

- 수동 입력 과정에서 동일 공구가 수십 가지 비표준 표현으로 기록됨
- 예: '충전식드릴', '드릴(배터리)', '무선전동드릴(20V)' → 모두 같은 제품

### 1.2 기존 방식의 한계

**규칙 기반(Rule-based) 방식:**
- 정규식, 형태소 분석기 → 구문적(Syntactic) 오류만 처리 가능
- 의미론적(Semantic) 맥락 이해 불가
  - 일본어 잔재: '기리(ぎり)' → '드릴비트' 변환 불가
  - 브랜드·규격 혼입: 'BOSCH 18V 충전드릴세트' → '드릴' 추론 불가
- 3,352개 변형에 수백 개 규칙 필요 → 유지보수 비용 급증

**수작업(Manual):**
- 숙련 작업자 기준 약 3~5일 소요 / 규모 확장 불가

### 1.3 연구 목적 및 기여

1. **평가 방법론 개선** — 검색 지식베이스와 평가 데이터를 완전 분리하여 기존 RAG v1의 데이터 누수 문제 제거
2. **개선된 RAG 파이프라인** — 4가지 기술적 개선(한국어 특화 임베딩, 하이브리드 검색, k값 확대, 카테고리 주입)
3. **오픈소스 LLM 비교 벤치마크** — 12개 모델(1.5B~9B)의 실험적 성능 비교
4. **더티데이터 유형별 성능 분석** — 11개 유형별 정확도 산출 및 실패 원인 메커니즘 규명
5. **LLM-only 비교 실험을 통한 RAG 역할 정량 분석** — RAG 없이 LLM 단독 성능 대비 RAG 기여도 측정

#### 왜 유형별로 성능이 다른가 — 핵심 메커니즘

**쉬운 유형 (93~96%): "수식어 제거 후 핵심어가 명확"**

동력원·속성·메타데이터 유형은 수식어('유선', '18V', '(40)')를 제거하면 핵심 공구명이 드러난다. BGE-m3-ko 임베딩이 수식어가 붙은 문자열과 표준명을 벡터 공간에서 가깝게 인코딩한다.

**오탈자 93.8%: 가장 중요한 발견**

가장 많은 유형(33.9%)임에도 93.8% 정확도를 달성. BGE-m3-ko(KURE 한국어 임베딩 1위, 1024차원)가 오탈자와 표준명을 벡터 공간에서 가깝게 인코딩하기 때문. 예: '경랑몽키'(오탈자) ↔ '경량 몽키렌치'(표준명) → 임베딩 유사도 높음. Baseline MiniLM(384차원 다국어)에서 같은 유형이 ~55%였던 것과 비교하면 **BGE-m3-ko 채택이 +38pp 개선의 핵심 원인**.

**일본어 잔재 47.1%: 구조적 실패 — 3가지 원인**

| 실패 원인 | 설명 |
|----------|------|
| 음운 단절 | `기리(錐)` ↔ `드릴비트`: 발음 완전 다름 → FAISS 유사도 낮음 |
| BM25 n-gram 불일치 | `기리`의 음절 bigram(기,리,기리)이 `드릴비트`(드,릴,비,트,드릴...)와 공통 없음 |
| LLM 사전지식 부재 | `기리=드릴비트` 매핑이 사전학습 코퍼스에 거의 없음 |

→ **모든 9개 모델이 23.5~52.9%**: 모델 교체로 해결 불가, 일본어→한국어 동의어 매핑 사전을 RAG 지식베이스에 명시 주입 필요

**주목할 이상치:**
- 세트/구성품: exaone3.5:7.8b가 **96.2%**로 1위 (gemma4:e4b 84.6% 대비 +11.6pp) — EXAONE의 한국 산업 현장 동의어 지식 우위 (L렌치=육각렌치 등)
- 속성 기입: granite4.1:3b가 **50.0%**로 이상 저조 — 3B 소형 모델의 규격 수치 포함 프롬프트 처리 한계

### 3.3 LLM-only vs RAG 비교

RAG의 실질적 기여를 정량화하기 위해, 동일 모델 4종에 대해 RAG 없이 LLM만으로 표준화를 수행하는 Zero-shot 실험을 추가 실시하였다(2026-05-09).

#### LLM-only Zero-shot vs RAG v2 비교표

| 모델               | LLM-only Exact | LLM-only Nearest | RAG v2 정확도 |   RAG 기여도   |
| ---------------- | :------------: | :--------------: | :--------: | :---------: |
| gemma4:e4b       |     27.4%      |      63.2%       | **88.5%**  | **+61.1pp** |
| gemma3:4b        |     23.0%      |      60.8%       | **84.5%**  | **+61.5pp** |
| exaone3.5:7.8b   |      9.4%      |      60.4%       | **79.2%**  | **+69.7pp** |
| deepseek-r1:1.5b |       0%       |       0.7%       | **78.4%**  | **+78.4pp** |

> **Exact:** 정답과 완전 일치 / **Nearest:** 의미적으로 유사한 표준명 선택 (정확한 표기 불일치 포함)

#### 핵심 해석 1: RAG = 표기 앵커링 (Output Anchoring)

LLM-only에서 **Exact(9~27%)와 Nearest(60~63%)의 큰 괴리**에 주목해야 한다.

- **Nearest 60%**: LLM이 어떤 공구인지는 개념적으로 이해하고 있음
- **Exact 9~27%**: 그러나 160개 표준명 중 정확한 표기·형식으로 출력하지 못함

즉, LLM은 공구의 개념은 파악하지만 표기 통일 능력이 없다. RAG는 검색된 후보 리스트를 제공함으로써 LLM의 출력을 표준 표기에 **앵커링(anchoring)**하는 역할을 한다. RAG의 핵심 기여는 새로운 지식 주입이 아니라 **출력 형식의 제약과 표준화**이다.

#### 핵심 해석 2: deepseek-r1:1.5b — 언어 한계 자체를 RAG가 우회

| 조건 | 성능 |
|------|------|
| LLM-only Exact | **0%** |
| LLM-only Nearest | 0.7% |
| RAG v2 | **78.4%** |

deepseek-r1:1.5b는 RAG 없이 한국어 공구명을 자유 생성하는 것 자체가 불가능하다(0%). Nearest도 0.7%에 불과하여 개념 이해조차 실패한다. 그러나 RAG 적용 시 78.4%를 달성한다.

이는 RAG가 단순히 정확도를 개선하는 것을 넘어, **모델의 언어적 한계 자체를 우회**하는 메커니즘임을 보여준다. 후보 리스트 중 선택 문제로 변환되면, 한국어 자유 생성 능력이 없는 소형 모델도 실용적 성능을 달성한다.

#### 유형별 LLM-only → RAG 개선 (gemma4:e4b 기준)

| 더티데이터 유형 | LLM-only | RAG v2 | 개선폭 |
|--------------|:--------:|:------:|:-----:|
| 동력원 명시 | 8.0% | 96.4% | **+88.4pp** |
| 오탈자 | 21.9% | 93.8% | **+71.9pp** |
| 일본어 잔재 | 19.0% | 47.1% | +28.0pp |

동력원 명시 유형에서 RAG 기여도가 가장 높다(+88.4pp). LLM은 '충전식전동드릴'이 드릴임을 이해하지만 정확한 표준명 '전동드릴'로 표기하지 못한다. RAG가 후보를 제공하는 즉시 거의 완벽한 선택이 이루어진다. 일본어 잔재는 RAG 적용 후에도 47.1%로 가장 낮아, 검색 지식베이스 자체의 보강이 필요함을 재확인한다.

### 3.4 주요 발견

**① RAG 환경에서 모델 크기 ≠ 성능**

| 비교                                                 | 결과                |
| -------------------------------------------------- | ----------------- |
| gemma3:4b (3.3GB) vs exaone3.5:7.8b (4.8GB)        | **84.5% > 79.2%** |
| deepseek-r1:1.5b (1.1GB) vs deepseek-r1:8b (5.2GB) | **78.1% ≒ 77.8%** |

→ 소형 모델도 도메인 특화 RAG로 대형 모델에 필적하는 성능 가능

**② 4가지 개선 요소 각각의 효과**

| 개선 항목         | 대표 효과                                    |
| ------------- | ---------------------------------------- |
| BGE-m3-ko 임베딩 | 오탈자 유형 93.8% 달성 — 한국어 형태소 변이를 동일 벡터로 인코딩 |
| BM25 하이브리드    | 순수 벡터 검색이 놓치는 어휘적 신호 보완                  |
| k=15 확대       | granite4.1:8b Fallback율 14.9% → 5.0%     |
| 카테고리 주입       | 동의어 공구 간 disambiguation 개선               |

**③ Fallback율 = 명령 이행 능력 지표**
- deepseek-r1:1.5b: 85.2% → 출력 형식 불준수 (JSON 미준수)
- 상위 3개 모델: 5~8% → 실사용 수준

**④ 처리 속도 (v1 vs v2 비교)**

| 항목        | v1 (Mac Mini M1 CPU) | v2 (RTX 5080 GPU)     |
| --------- | -------------------- | --------------------- |
| 임베딩 시간    | 수 분 (건당 처리)          | **약 10초** (3,352건 일괄) |
| LLM 처리 속도 | 0.06~0.84건/초 (추정)    | **1.2~2.0건/초**        |
| 전체 처리 시간  | 1~13시간               | **30~50분**            |

## 4. 결론

### 4.1 연구 결과 요약

1. **LLM+RAG로 비정형 공구 이름 표준화 가능:** 개선 RAG는 기본 RAG 대비 +33.3%p 향상, 최고 88.47% 달성
2. **도메인 특화 검색 아키텍처가 모델 크기보다 중요:** 소형 모델(3~4GB)이 대형 모델(7.8B)에 필적하거나 초월
3. **데이터 누수 수정으로 신뢰할 수 있는 평가 기준 확립:** 97.88% (v1) → 88.47% (v2)의 의미 차이 규명
4. **더티데이터 유형별 성능 격차 규명:** 동력원·속성·오탈자(93~96%) vs. 일본어 잔재(47.1%) — 유형별 실패 메커니즘 식별
5. **LLM-only 비교로 RAG 역할 정량화:** RAG 기여도 +61~78pp — LLM 단독(0~27%)은 실용 불가, RAG가 표기 앵커링 및 언어 한계 우회 역할 수행

### 4.2 연구 한계

- 정답지 커버리지: 457/3,352 = **13.6%** — 전체 더티데이터 분포 대표성 한계
- 17GB 이상 모델: 단일 소비자급 GPU에서 실용 불가 (CPU 오프로드 시 ~0.03건/초)
- deepseek-r1:1.5b: 85.2% Fallback율 → 실사용 적합성 낮음
- 일본어 잔재 유형(n=17): 소표본으로 통계적 안정성 제한

### 4.3 향후 연구 방향

| 방향 | 내용 |
|------|------|
| ① 일본어 잔재 해결 | 일본어→한국어 공구 동의어 사전을 RAG 지식베이스에 명시 주입 |
| ② Human-in-the-Loop | 기타·일본어 잔재 유형 저신뢰도 예측 → 전문가 검수 큐 자동 분류 |
| ③ 정답지 확장 | 전체 3,352건 완전 정답지 구축으로 평가 대표성 강화 |
