## 1. 데이터 정제는 왜 병목인가

### 1.1 현실: 데이터는 쌓이지만, 쓸 수 있는 데이터는 없다

업계 조사 결과에 따르면 데이터 과학자는 업무 시간의 약 60~80%를 데이터 수집·정제에 소비한다 (CrowdFlower, 2016). 학술 연구도 이를 뒷받침한다. Zhang & Huang (2024)은 "실세계 데이터셋은 다양한 품질 문제로 인해 데이터 정제가 여전히 노동 집약적 과정으로 남아 있다"고 지적하며 [12], Glock & Korom (2025)은 오스트리아 우체국과의 협업에서 LLM이 수작업 대비 정제 비용을 현저히 줄임을 실증하였다 [10]. Karaca (2024)는 텍스트 전처리 품질이 분류 정확도에 직접적인 영향을 미침을 정량 분석하였다 [13].

AI·분석 프로젝트의 실패 원인 1위는 "모델이 나빠서"가 아니라 **"입력 데이터가 더러워서"** 인 경우가 대부분이다. 정선우 외 (2023)는 오염된 훈련 데이터가 LLM 기반 시스템의 출력 신뢰도를 직접 저하시킴을 국내 연구로 확인하였다 [14].

---

### 1.2 구체적 사례: 서울시 공구대여 데이터

| 항목 | 수치 |
|------|------|
| 전체 대여 기록 | 11,525건 |
| 고유 공구 이름 | **3,352개** |
| 실제 공구 종류 (표준명) | **약 160종** |
| 1종당 평균 표기 변형 수 | **~21가지** |

동일 제품의 다양한 표기 변형은 사용자가 "자신에게 의미 있는 정보"(브랜드, 동력원, 규격 등)를 추가하는 자연스러운 행동의 결과다 (Christian & Okorie, 2013) [17]. 그러나 시스템 입장에서는 비표준 데이터가 된다.

---

### 1.3 비정형 더티데이터의 유형 분류

본 연구는 Kim et al. (2003) [18]의 더티데이터 분류 체계를 공구 도메인에 특화하여 적용하였다. Kim et al.은 더티데이터를 missing data, wrong data, non-standard representation 등으로 체계적으로 분류한 선도적 연구로, 본 연구의 5대 유형 분류는 이를 재적용한 것이다.

| 유형 | 실제 예시 | 발생 원인 |
|------|---------|---------|
| **속성·규격 혼입** | '180mm 그라인더', '8인치 몽키렌치' | 사용자가 크기·규격을 공구명에 포함 |
| **동력원 명시** | '충전식전동드릴', '에어임팩트렌치' | 동력원 구분을 이름에 직접 기재 |
| **오탈자·오표기** | '경랑몽키'→경량몽키, '랜지'→렌치 | 입력 오류 또는 구어체 표기 |
| **일본어 잔재** | '기리'(드릴비트), '뺀치'(펜치), '노기스'(버니어캘리퍼스) | 건설·제조 현장 일본어 유래 표현 |
| **세트·복합** | '글루건&글루스틱', '드라이버/렌치세트' | 여러 공구를 하나의 이름으로 표기 |

---

### 1.4 수작업 정제의 한계

**규칙 기반 (Rule-based):** 3,352개 변형에 수백 개 규칙 필요 → 유지보수 비용 급증. 데이터 업데이트 시 규칙도 지속 추가 필요.

**수작업 (Manual):** 숙련 작업자 기준 약 3~5일 소요. 규모 확장 불가.

Glock & Korom (2025)은 전통적 규칙 기반 도구(Raha, Baran, Autoencoder)보다 LLM이 **예상치 못한 맥락적 오류**를 더 잘 탐지함을 실증하였다 [10]. Zhang & Huang (2024)은 기존 시스템이 오류 데이터에서 파생된 통계 규칙에 의존하는 한계를 지적하고, LLM의 의미론적 이해로 이를 극복할 수 있음을 보였다 [12].

## 2. LLM+RAG로 어떻게 해결하는가

### 2.1 핵심 아이디어: 분류 문제로 재정의

비정형 공구 이름을 **160종 표준명 중 하나로 분류하는 문제**로 재정의한다.

```
입력: '충전식전동드릴 (보쉬 GSR 18V)'
출력: { standard_name: '충전드릴', brand: '보쉬', power_source: '충전식(무선)', specification: '18V' }
```

이는 비표준 텍스트를 LLM Few-Shot으로 표준화하는 PolyNorm (Wong et al., 2025) [1]이나, 자동 텍스트 정규화로 하위 분류 정확도를 향상시킨 Nguyen et al. (2023) [15]과 동일한 NLP 패러다임이다.

---

### 2.2 RAG v2 파이프라인

```
[더티 공구명 입력]
        ↓
[1. 임베딩 (GPU 배치)] dragonkue/BGE-m3-ko | ~11초/3,352건
        ↓
[2. 하이브리드 검색] FAISS(60%) + BM25(40%) → 후보 15개
        ↓
[3. LLM 분류] Ollama 로컬 | JSON 출력
        ↓
[4. Fallback] LLM 후보 외 응답 → top-1 강제 대체
        ↓
[출력: 표준화된 공구명 + 브랜드 + 동력원 + 규격]
```

RAG는 LLM의 환각(hallucination) 문제를 완화하고 도메인 지식을 효과적으로 주입하는 방법론으로 검증되었다 (Amugongo et al., 2025) [5]. 검색 품질(k값, 하이브리드 검색)이 최종 생성 품질에 미치는 영향은 GAN et al. (2025)의 종합 분석에서 상세히 다루어진다 [6].

임베딩 모델 선택에서는 한국어 도메인 특화 임베딩 모델이 범용 다국어 임베딩 대비 검색 성능을 유의미하게 향상시킴이 실증되어 (Hwang et al., 2025) [9], BGE-m3-ko를 채택하였다.

---

### 2.3 1차 연구(RAG v1)의 방법론적 문제와 개선

| 항목 | RAG v1 (1차) | RAG v2 (본 연구) |
|------|------------|----------------|
| 벡터 DB 입력 | 386개 정답 쌍 | **160개 표준명 목록만** |
| 평가 데이터 | 동일한 386개 쌍 | **457개 (DB와 완전 분리)** |
| 문제 | 정답 힌트 노출 (데이터 누수) | Train/Test 완전 분리 |
| 최고 정확도 | 97.88% (과대 추정) | **88.47% (신뢰 가능)** |

RAG v1의 97.88%는 "정답이 컨텍스트에 포함된 상태에서 복사하는 능력"을 측정한 것에 가깝다. 정선우 외 (2023)는 LLM 컨텍스트에 평가 데이터와 유사한 정보가 포함될 경우 출력 신뢰도가 허위로 높아지는 현상을 분석하였다 [14].

---

### 2.4 개선 효과: +33%p 향상

| 단계 | 최고 정확도 |
|------|-----------|
| Baseline (MiniLM, k=5) | 55.21% |
| Improved (BGE-m3-ko, BM25, k=15, 카테고리 주입) | **88.47%** |
| **개선폭** | **+33.26%p** |

RAG 방식은 도메인 지식이 자주 변경되는 환경에서 Fine-tuning 대비 유리하다. Ovadia et al. (2023)은 동일 도메인 지식 주입 시 RAG가 Fine-tuning보다 적은 비용으로 유사하거나 더 나은 성능을 달성하며, 특히 도메인 업데이트가 잦을수록 RAG의 유연성이 우월함을 실증하였다 [16].

## 3. 왜 로컬 LLM이어야 하는가

### 이유 1. 보안 · 개인정보 보호

```
클라우드 API: [내부 데이터] → [인터넷] → [외부 서버] ← ❌ 데이터 유출 위험
로컬 LLM:    [내부 데이터] → [내부 GPU]              ← ✅ 데이터가 밖으로 나가지 않음
```

Amugongo et al. (2025)는 의료 RAG 시스템 체계적 검토에서 데이터 프라이버시와 보안이 LLM 도입의 핵심 장벽이며, 로컬·온프레미스 배포가 이를 해결하는 주요 접근법으로 반복 권고됨을 확인하였다 [5]. Belcak et al. (2025)은 SLM의 로컬 실행 이점으로 "stronger data control(데이터 통제 강화)"을 명시적으로 언급하며 소비자급 GPU에서의 오프라인 추론을 시연하였다 [7].

---

### 이유 2. 비용 구조의 차이

| 항목 | 클라우드 API (GPT-4o 기준) | 로컬 LLM |
|------|--------------------------|---------|
| 3,352건 처리 | 입력 ~$4 + 출력 ~$3 = **약 $7** | 전기요금 **약 $0.05** |
| 100,000건 처리 | **약 $210** | **약 $1.5** |
| 월 100만건 처리 | **약 $2,100/월** | 서버 초기비용 후 **월 $15** |

WINGPT Team (2025)은 LLM 추론을 생산 경제학으로 분석하여 규모의 경제가 작동하는 구간에서 온프레미스 추론의 비용 우위가 급격히 증가함을 실증하였다 [2].

---

### 이유 3. 운영 안정성 · 독립성

| 상황 | 클라우드 API | 로컬 LLM |
|------|------------|---------|
| 인터넷 장애 | ❌ 서비스 불가 | ✅ 정상 운영 |
| API Rate Limit | ❌ 대기 필요 | ✅ 제한 없음 |
| 배치 처리 자동화 | 제한적 | ✅ 자유로운 스케줄링 |

Belcak et al. (2025)은 인터넷 연결 없이도 소비자급 GPU에서 실시간 처리가 가능한 오프라인 에이전트 추론의 실현 가능성을 시연하였다 [7].

---

### 이유 4. 도메인 커스터마이징

Ovadia et al. (2023)의 Fine-tuning vs RAG 비교 연구에서, 도메인 지식이 자주 변경되는 환경에서는 모델 재학습 없이 지식 베이스만 교체할 수 있는 RAG가 우월함이 실증되었다 [16]. 공구 표준 개정, 신규 브랜드 추가 등의 상황에서 정답지(RAG DB)만 갱신하면 되는 본 시스템의 설계 철학과 부합한다. Campo et al. (2025)은 도메인 특화 정보를 RAG로 주입하여 범용 LLM을 도메인 전문가 수준으로 향상시키는 사례를 실증하였다 [8].

---

### 4.2 소형 모델의 실용성

Belcak et al. (2025)은 소수의 전문화된 작업을 반복 수행하는 에이전트 시스템에서 SLM이 대형 모델에 비해 충분히 강력하고 더 적합하며 경제적으로 우월하다고 주장하였다 [7].

본 연구 결과가 이를 뒷받침한다:
- **deepseek-r1:1.5b (1.1GB)** → 78.05% 정확도 (실무 적용 가능한 수준)
- **exaone3.5:2.4b (1.6GB)** → 74.06% (VRAM이 제한된 환경에서도 구동 가능)

---

### 4.3 Trade-Off Score 분석

α를 업무 우선순위에 따라 조정:
```
Trade-Off Score = α × 정확도 + (1-α) × 속도_점수
```

| 모델 | α=0.75 (정확도 우선) | α=0.50 (균형) | α=0.25 (속도 우선) |
|------|-------------------:|-------------:|------------------:|
| **gemma4:e4b** | **1위** | 2위 | 3위 |
| **gemma3:4b** | 2위 | **1위** | 2위 |
| **gemma4:e2b** | 4위 | 3위 | **1위** |

이는 복수의 목표(정확도, 속도)가 상충할 때 가중치 α를 통해 의사결정자의 우선순위를 반영하는 다속성 효용 분석(MAUT) 프레임워크를 적용한 것이다 (Keeney, 1975) [19].

---

### 4.4 모델 크기 ≠ 성능: 아키텍처가 중요하다

**VRAM 한계로 실험 제외된 대형 모델:** deepseek-r1:32b, granite4.1:30b 등 17GB 초과 모델은 RTX 5080(17.1GB VRAM) 기준 CPU 오프로드가 발생하여 처리속도가 0.03개/초 수준으로 실용 불가.

Belcak et al. (2025)은 태스크 특화(task specialization)가 모델 크기보다 성능 결정의 핵심 요인임을 주장하며, Wang et al. (2025)은 전자상거래 상품명 매핑에서 도메인 특화가 성능에 미치는 영향을 실증하였다 [7, 4].

## 5. LLM은 어디서 실수하는가 — 오류 유형 및 더티데이터 유형별 성능

---

### 5.1 오류의 두 가지 원인: RAG 단계 vs LLM 단계

LLM+RAG 파이프라인의 오류는 발생 위치에 따라 명확히 두 단계로 분류된다.

```
[더티 공구명] → [RAG 검색] → [LLM 분류]
                    ↑                ↑
              단계 1 실패        단계 2 실패
              (정답이 후보에     (정답이 후보에
               포함 안 됨)       있었지만 틀림)
```

## 6. LLM-only vs RAG 비교 실험

> 실험 완료일: 2026-05-09 | 평가 데이터: 정답지 v2 동일 457건 | 방식: Zero-shot (RAG 없음, LLM 자체 지식만 활용)

### 6.1 실험 설계

RAG가 실제로 성능에 기여하는지, 아니면 LLM의 사전학습 지식만으로도 충분한지를 검증하기 위해 **LLM-only Zero-shot 비교 실험**을 수행하였다. RAG 파이프라인의 검색 단계를 제거하고, 동일 GT 457건에 대해 표준명 목록(160종)만을 시스템 프롬프트로 제공한 뒤 LLM 자체 지식으로 표준화하도록 하였다.

**평가 지표 정의:**
- **LLM-only exact**: 표준명과 정확히 일치하는 비율 (정확 일치)
- **LLM-only nearest**: 의미상 가장 유사한 표준명을 선택한 비율 (최근접 일치, 표기 차이 허용)
- **RAG v2 Improved**: 본 연구의 최종 파이프라인 결과 (섹션 4.1과 동일)

---

### 6.2 전체 정확도 비교 — LLM-only vs RAG

| 모델 | LLM-only exact | LLM-only nearest | RAG v2 Improved | RAG 기여 (vs exact) |
|------|:--------------:|:----------------:|:---------------:|:-------------------:|
| gemma4:e4b | 27.4% | 63.2% | **88.5%** | **+61.1pp** |
| gemma3:4b | 23.0% | 60.8% | **84.5%** | **+61.5pp** |
| exaone3.5:7.8b | 9.4% | 60.4% | **79.2%** | **+69.7pp** |
| deepseek-r1:1.5b | 0% | 0.7% | **78.4%** | **+78.4pp** |

> **주목할 수치**: 모든 모델에서 RAG 도입 시 exact 기준 +61~+78pp의 절대적 성능 향상이 관측되었다. LLM 단독으로는 최고 모델(gemma4:e4b)도 27.4%에 그쳐 실용 수준에 미치지 못한다.

---

### 6.3 더티데이터 유형별 비교 — gemma4:e4b 기준

| 유형 | LLM-only exact | RAG v2 Improved | RAG 기여 |
|------|:--------------:|:---------------:|:--------:|
| 동력원 명시 | 8.0% | **96.4%** | **+88.4pp** |
| 오탈자 | 21.9% | **93.8%** | **+71.9pp** |
| 속성 기입 | 55.0% | **95.0%** | **+40.0pp** |
| 메타데이터 | 45.5% | **95.5%** | **+50.0pp** |
| 일본어 잔재 | 19.0% | **47.1%** | **+28.1pp** |

유형별로 RAG의 기여 폭은 +28.1pp(일본어 잔재)에서 +88.4pp(동력원 명시)에 이르기까지 크게 다르다. LLM이 사전학습 지식만으로 비교적 잘 처리하는 유형(속성 기입: 55.0%, 메타데이터: 45.5%)에서도 RAG 도입 시 정확도가 +40~50pp 추가 향상된다는 점은, RAG의 역할이 단순한 지식 보완이 아닌 **표기 고정(anchoring)** 임을 시사한다.

---

### 6.4 핵심 해석

**해석 1 — RAG의 역할은 "지식 주입"이 아닌 "표기 앵커링(anchoring)"이다**

LLM-only nearest(최근접 일치)와 exact(정확 일치) 간 평균 격차는 **약 35pp**에 달한다. 즉, LLM은 해당 공구가 무엇인지 개념적으로는 파악하지만(nearest는 높음), 시스템에서 사용하는 정확한 표준 표기를 재현하지 못한다(exact는 낮음). RAG는 후보 목록을 통해 "어떤 표기를 사용해야 하는가"를 앵커링함으로써 이 간극을 메운다. 이는 RAG가 LLM의 **언어적 지식**보다 **표기 정밀도**를 보완하는 역할을 수행함을 의미한다.

**해석 2 — RAG는 언어 능력 한계 자체를 우회한다: deepseek-r1:1.5b 사례**

deepseek-r1:1.5b는 1.5B 파라미터의 영어·중국어 중심 모델로, LLM-only 조건에서 exact 0%, nearest 0.7%를 기록하였다. 이는 API 설정 오류가 아니라, 해당 모델이 한국어 자유 생성 자체에 근본적인 한계를 가지기 때문이다. 그러나 RAG 조건에서는 **78.4%**를 달성하였다. RAG가 제공하는 후보 목록이 한국어 생성 능력의 부재를 우회하여 **선택(classification) 과제**로 문제를 변환함으로써, 언어 능력과 도메인 지식의 한계를 동시에 극복한 것이다.

**해석 3 — 일본어 잔재에서 RAG 역효과 가설 기각**

일본어 잔재 유형에서 RAG의 효과가 제한적(+28.1pp, 최종 47.1%)이라는 결과로 인해, "RAG가 오히려 잘못된 후보를 제공하여 혼란을 가중시킨다"는 역효과 가설이 제기될 수 있었다. 그러나 LLM-only 조건에서의 성능(19.0%)과 비교하면 RAG 도입 후에도 +28.1pp의 순 향상이 확인된다. 따라서 일본어 잔재에서의 낮은 절대 정확도(47.1%)는 RAG의 역효과가 아닌, **임베딩·BM25 검색 단계에서의 구조적 한계**(음운 단절로 인한 후보 풀 품질 저하)에서 비롯된 것으로 해석된다.

## 7. 실제 업무에 적용한다면

### 7.1 어떤 데이터에 적용 가능한가

| 도메인 | 더티 데이터 예시 | 표준화 목표 |
|--------|--------------|-----------|
| **공공·행정** | 직업 분류, 주소, 기관명 | KS 표준 코드 |
| **의료** | 증상명, 약품명 | ICD-10, ATC 코드 |
| **전자상거래** | 상품명, 브랜드명 | 카테고리 코드 |
| **인사·채용** | 직무명, 기술스택명 | 표준 직무 코드 |
| **제조·ERP** | 자재명, 부품 코드 | BOM 표준 코드 |

Amugongo et al. (2025)는 의료 RAG에서 임상 데이터 정규화, 의학 용어 표준화에 RAG 기반 LLM이 유효함을 확인하였고 [5], Wang et al. (2025)은 전자상거래 상품명 매핑에서 cold-start 문제 극복 방법론을 제시하였다 [4].

### 7.2 구현 로드맵 — 오류 분석 기반 개선 단계 포함

```
Week 1-2: 정답지(Ground Truth) 구축
  → 도메인 전문가 + 카탈로그 참조, 500~1,000개 엔트리 목표
  → 일본어 잔재 사전, 오탈자 패턴 사전 병행 구축 (RAG 검색 실패 ~25건 해결)

Week 3: 기술 스택 설치
  → Ollama, sentence-transformers, faiss-cpu, rank-bm25

Week 4: 시범 운영 + 오류 유형 진단
  → 1,000건 샘플 정확도 측정
  → 오류 유형 분류: RAG 실패 vs LLM 실패 구분 (본 연구 프레임워크 적용)

Month 2: 유형별 개선 적용
  → RAG 실패 케이스: 전처리 사전 확충, 임베딩 재구성
  → LLM 실패 케이스: 취약 유형 특화 프롬프트 (세트/단품, 동력원 구분)

Month 3+: 전체 데이터 배치 처리 + Human-in-the-Loop 통합
  → 낮은 신뢰도 항목만 인간 검수 (Dhakal et al., 2025) [3]
  → 신규 데이터 자동 파이프라인 연동
```

---

### 7.3 기대 효과 및 한계

**기대 효과:**

| 지표 | 현재 (수작업) | 도입 후 |
|------|-------------|---------|
| 처리 속도 | 3~5일/3,000건 | **30~50분/3,000건** |
| 인력 투입 | 담당자 상시 필요 | 최초 정답지 구축만 |
| 일관성 | 담당자에 따라 편차 | 동일 규칙 100% 적용 |
| 정확도 | 숙련자 ~95% | **RAG+LLM: 74~88%** |

**주요 한계 및 잔여 오류:**

1. **RAG 구조 한계 (~25건)**: 일본어 잔재, 모델번호만 포함된 입력은 현재 RAG로 검색 불가 → 전처리 레이어 추가로 개선 여지
2. **세트·단품 혼동 (오답의 13.5%)**: '글루건&글루스틱'처럼 복합 공구명에서 주공구 판단 실패 → 프롬프트 엔지니어링으로 개선 가능
3. **동력원 분류 오류 (7.7%)**: 충전식=무선 등 동의어 관계 미인식 → 동의어 사전 또는 카테고리 정보 추가
4. **대형 모델(17GB+) 실행 불가**: RTX 5080 기준 30B 이상 모델 0.03개/초로 실용 불가

Belcak et al. (2025)은 반복적·전문화된 에이전트 태스크에서 SLM이 충분히 효과적임을 주장하며 [7], 본 연구에서 74~88% 정확도를 달성한 3~9.6GB 모델들이 이를 실험적으로 뒷받침한다.

## 8. 결론 및 제언

### 핵심 메시지 4가지

**① 비정형 데이터 정제는 LLM+RAG로 해결 가능한 문제다**

Kim et al. (2003)의 더티데이터 분류 체계 [18], Zhang & Huang (2024)의 LLM 기반 정제 실증 [12], Glock & Korom (2025)의 기업 환경 적용 사례 [10]가 이론적 근거를 제공하며, 본 연구의 baseline 55% → improved 88.47% (+33%p) 결과가 실증적으로 뒷받침한다.

**② 오류 유형을 알아야 개선 방향이 보인다**

오답의 46%는 RAG 단계 구조 문제(~25건 고정), 44%는 LLM 추론 문제(모델별 편차 큼)다. 이 구분 없이 단순히 "더 좋은 모델"로 교체하는 것은 절반의 문제만 해결한다. **RAG 개선 + LLM 프롬프트 특화**라는 이중 전략이 필요하다.

**③ RAG는 표기 앵커(anchor) 역할을 한다**

LLM-only 비교 실험 결과, LLM은 공구의 개념적 범주를 인식하지만(nearest: 최고 63.2%) 정확한 표기를 재현하지 못한다(exact: 최고 27.4%). RAG는 후보 목록을 통해 표기를 고정(anchoring)함으로써 평균 +61~78pp의 성능 향상을 제공한다. 이는 RAG가 단순한 지식 보완 도구가 아니라, **표준 표기 준수를 강제하는 구조적 장치**로 기능함을 의미한다.

**④ 로컬 LLM은 보안·비용·안정성에서 클라우드 API의 실질적 대안이다**

WINGPT Team (2025)의 추론 경제학 분석 [2], Belcak et al. (2025)의 SLM 에이전트 연구 [7], Amugongo et al. (2025)의 의료 프라이버시 요건 분석 [5]이 공통적으로 로컬 배포의 우위를 지지한다.
