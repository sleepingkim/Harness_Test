## 1. 데이터 정제는 왜 병목인가

### 1.1 현실: 데이터는 쌓이지만, 쓸 수 있는 데이터는 없다

디지털 전환이 진행될수록 기관과 기업에는 방대한 데이터가 축적된다.
그러나 데이터가 많다고 해서 활용 가능한 데이터가 많은 것은 아니다.

> **"Data Scientists spend 80% of their time cleaning data."** — Forbes (2016)

이 수치는 10년이 지난 지금도 크게 바뀌지 않았다. AI·분석 프로젝트의 실패 원인 1위는
"모델이 나빠서"가 아니라 **"입력 데이터가 더러워서"** 인 경우가 대부분이다.

### 1.2 구체적 사례: 서울시 공구대여 데이터

본 연구의 대상 데이터는 서울시가 공개한 공구대여 기록이다.

| 항목 | 수치 |
|------|------|
| 전체 대여 기록 | 11,525건 |
| 고유 공구 이름 | **3,352개** |
| 실제 공구 종류 (표준명) | **약 160종** |
| 1종당 평균 표기 변형 수 | **~21가지** |

같은 '망치' 하나를 3,352개의 기록에서 사람들은 이렇게 입력했다:

```
망치, 해머, 함마, 햄머, 망치(대), 망치(소), 해머-800g, 
고무망치, 노루발망치, 우레탄해머, 함마200g, 장도리 ...
```

이 데이터를 그대로 분석하면, "가장 많이 빌린 공구 TOP 5"도 제대로 집계할 수 없다.

### 1.3 비정형 더티데이터의 5대 유형

| 유형 | 예시 | 비율 |
|------|------|------|
| **속성 혼입** | '180mm 그라인더', 'HiKOKI 전기드릴' | 가장 빈번 |
| **동력원 명시** | '충전식전동드릴', '에어임팩트렌치' | 높음 |
| **오탈자·오표기** | '경랑몽키', '랜지' → 렌치 | 중간 |
| **일본어 잔재** | '기리'(드릴비트), '뺀치'(펜치), '빠루'(못뽑이) | 중간 |
| **세트·복합** | '글루건&심', '드라이버/렌치세트' | 낮음 |

### 1.4 수작업 정제의 한계

기존 방법론은 두 가지다.

**규칙 기반 (Rule-based):**
- 장점: 빠르고 결정론적
- 한계: 규칙 작성에 도메인 전문가 시간 투입 → 3,352개 변형에 수백 개 규칙 필요
- 유지보수: 데이터가 업데이트되면 규칙도 계속 추가해야 함

**수작업 (Manual):**
- 3,352개를 사람이 직접 분류 → 숙련 작업자 기준 **약 3~5일 소요**
- 오류 발생, 일관성 부재
- 규모 확장 불가

**→ 결론**: 수작업이나 규칙으로는 비용·시간·확장성 모두에서 한계. LLM의 언어 이해 능력이 필요하다.

## 2. LLM+RAG로 어떻게 해결하는가

### 2.1 핵심 아이디어: 분류 문제로 재정의

비정형 공구 이름을 **160종 표준명 중 하나로 분류하는 문제**로 재정의한다.

```
입력: '충전식전동드릴 (보쉬 GSR 18V)'
출력: { standard_name: '충전드릴', brand: '보쉬', power_source: '충전식(무선)', specification: '18V' }
```

LLM 혼자 시키면 할루시네이션 위험이 있다.
→ **RAG(검색 증강 생성)** 로 표준 후보 목록을 먼저 검색해 프롬프트에 제공.

### 2.2 RAG v2 파이프라인

```
[더티 공구명 입력]
        ↓
[1. 임베딩 (GPU 배치)]
  dragonkue/BGE-m3-ko (한국어 특화)
  3,352개 일괄 처리 → ~11초
        ↓
[2. 하이브리드 검색]
  FAISS 벡터 검색 (60%) + BM25 키워드 검색 (40%)
  → 표준 공구명 후보 15개 추출
        ↓
[3. LLM 분류 (Ollama 로컬)]
  역할: 한국어 공구 이름 분류 전문가
  입력: 더티명 + 후보 15개 + 카테고리 정보
  출력: JSON { standard_name, brand, power_source, specification }
        ↓
[4. Fallback 처리]
  LLM 출력이 후보 외: top-1으로 강제 대체 (비율 측정)
        ↓
[출력: 표준화된 공구명]
```

### 2.3 1차 연구(RAG v1)의 방법론적 문제와 개선

1차 연구에서 97%+ 정확도를 달성했으나, 평가 설계에 **데이터 누수(Data Leakage)** 문제가 있었다.

| 항목 | RAG v1 (1차) | RAG v2 (본 연구) |
|------|------------|----------------|
| 벡터 DB 입력 | 386개 정답 쌍 (original→standard) | **160개 표준명 목록만** |
| 평가 데이터 | 동일한 386개 쌍 | 별도 457개 정답 쌍 |
| 문제 | 평가 항목이 DB에 있어 "정답 힌트" 존재 | Train/Test 완전 분리 |
| 측정 내용 | 컨텍스트 복사 능력 | **진정한 의미론적 분류 능력** |
| 최고 정확도 | 97.88% (과대 추정) | **88.47% (신뢰 가능)** |

### 2.4 개선 효과: +33%p 향상

| 단계 | 최고 정확도 | 핵심 변경 |
|------|-----------|---------|
| Baseline (MiniLM, k=5) | 55.21% | 기본 RAG |
| Improved (BGE-m3-ko, BM25, k=15, 카테고리) | **88.47%** | 4가지 개선 적용 |
| **개선폭** | **+33.26%p** | — |

> Baseline → Improved 9개 모델 평균: **55.21% → 79.26% (+24.05%p)**

## 3. 왜 로컬 LLM이어야 하는가

클라우드 API(GPT-4o, Claude API 등)도 충분히 강력하다.
그럼에도 **로컬 LLM(Ollama)** 을 선택하는 데는 4가지 이유가 있다.

### 이유 1. 보안 · 개인정보 보호

공공기관·기업 데이터에는 개인정보, 영업비밀, 미공개 정보가 포함될 수 있다.
외부 API에 데이터를 전송하는 것은 **정보보안 정책, 개인정보보호법, 의료법** 등에 저촉될 수 있다.

```
클라우드 API: [내부 데이터] → [인터넷] → [외부 서버] ← ❌ 데이터 유출 위험
로컬 LLM:    [내부 데이터] → [내부 GPU] ← ✅ 데이터가 밖으로 나가지 않음
```

특히 의료 데이터, 금융 거래 기록, 인사 데이터처럼 민감한 데이터일수록 로컬이 필수다.

### 이유 2. 비용 구조의 차이

| 항목 | 클라우드 API (GPT-4o 기준) | 로컬 LLM |
|------|--------------------------|---------|
| 3,352건 처리 | 입력 ~$4 + 출력 ~$3 = **약 $7** | 전기요금 **약 $0.05** |
| 100,000건 처리 | **약 $210** | **약 $1.5** |
| 월 100만건 처리 | **약 $2,100/월** | 서버 초기비용 후 **월 $15** |
| 데이터 증가 시 | 비용 선형 증가 | 거의 고정 비용 |

> 초기 GPU 서버 투자는 발생하지만, 대량·반복 처리 시 **손익분기점이 빠름**.
> 특히 정기적으로 데이터를 정제해야 하는 업무라면 로컬이 압도적으로 경제적.

### 이유 3. 운영 안정성 · 독립성

| 상황 | 클라우드 API | 로컬 LLM |
|------|------------|---------|
| 인터넷 장애 | ❌ 서비스 불가 | ✅ 정상 운영 |
| API Rate Limit | ❌ 대기 필요 | ✅ 제한 없음 |
| API 서비스 종료/가격 변경 | ❌ 즉각 영향 | ✅ 무관 |
| 배치 처리 (야간 자동화) | 제한적 | ✅ 자유로운 스케줄링 |

### 이유 4. 도메인 커스터마이징

로컬 환경에서는 프롬프트, 후처리 로직, Fallback 정책을 **자유롭게 수정**할 수 있다.
도메인 특화 용어 사전, 업무 규칙, 특수 처리 케이스를 시스템에 직접 반영 가능하다.

본 연구에서도 "해머드릴은 망치드릴로 변환하지 않는다"는 복합어 규칙을 정답지에 반영했는데,
이런 세밀한 조정은 범용 API에서는 할 수 없거나 매우 어렵다.

## 4. 속도 vs 정확도 트레이드오프

### 4.1 전체 실험 결과 (12개 모델/변형)

| 순위 | 모델 | 방식 | 정확도 | 속도 | 3,352건 처리 |
|:---:|------|------|-------:|-----:|----------:|
| 🥇 1 | gemma4:e4b (9.6GB) | improved | **88.47%** | 1.58개/초 | 35분 |
| 🥈 2 | gemma3:4b (3.3GB) | improved | **84.48%** | 1.77개/초 | 31분 |
| 🥉 3 | granite4.1:8b (5.3GB) | improved | **82.48%** | 1.21개/초 | 46분 |
| 4 | gemma4:e2b (7.2GB) | improved | **80.93%** | 1.93개/초 | 29분 |
| 5 | exaone3.5:7.8b (4.8GB) | improved | **79.16%** | 1.23개/초 | 45분 |
| 6 | deepseek-r1:1.5b (1.1GB) | improved | **78.05%** | 1.49개/초 | 37분 |
| 7 | deepseek-r1:8b (5.2GB) | improved | **77.83%** | 1.40개/초 | 40분 |
| 8 | exaone3.5:2.4b (1.6GB) | improved | **74.06%** | 1.58개/초 | 35분 |
| 9 | granite4.1:3b (2.1GB) | improved | **67.85%** | 1.53개/초 | 36분 |

> `deepseek-r1:1.5b` improved: 78.05% 정확도이나 **Fallback율 85.2%** — LLM이 후보 외 응답을 많이 해서 강제 대체된 비율이 높음. 실사용 시 주의 필요.

### 4.2 시나리오별 최적 모델 선택

업무 상황에 따라 적합한 모델이 달라진다.

**① 정확도 최우선 (고부가가치 데이터 정제)**
```
추천: gemma4:e4b
→ 88.47% 정확도 | 35분/3,352건 | VRAM 9.6GB 필요
→ 적용: 의료 데이터 코딩, 법적 문서 분류, 금융 마스터데이터 정비
```

**② 속도·정확도 균형 (일반 업무 자동화)**
```
추천: gemma3:4b 또는 gemma4:e2b
→ 84.48%(31분) 또는 80.93%(29분)
→ 적용: ERP 품목 코드 정제, 공공데이터 표준화, 정기 배치 처리
```

**③ 경량 환경 (GPU 없거나 VRAM 제한)**
```
추천: exaone3.5:2.4b 또는 deepseek-r1:1.5b
→ 74.06%(35분, 1.6GB) 또는 78.05%(37분, 1.1GB)
→ 적용: 소규모 조직, 테스트 환경, Edge 배포
```

### 4.3 Trade-Off Score 분석

α를 업무 우선순위에 따라 조정:
```
Trade-Off Score = α × 정확도 + (1-α) × 속도_점수
```

| 모델 | α=0.75 (정확도↑) | α=0.50 (균형) | α=0.25 (속도↑) |
|------|----------------:|-------------:|---------------:|
| **gemma4:e4b** | **1위** | 2위 | 3위 |
| **gemma3:4b** | 2위 | **1위** | 2위 |
| **gemma4:e2b** | 4위 | 3위 | **1위** |
| exaone3.5:7.8b | 5위 | 5위 | 5위 |
| deepseek-r1:8b | 7위 | 7위 | 4위 |

> **핵심 인사이트**: Gemma 계열(Google)이 이 태스크에서 일관되게 강세를 보인다.
> 특히 gemma4:e4b는 속도가 중간 수준임에도 정확도가 압도적이어서 대부분의 시나리오에서 상위권.

## 5. 실제 업무에 적용한다면

### 5.1 어떤 데이터에 적용 가능한가

비정형 범주형 데이터라면 도메인에 관계없이 동일한 접근법이 적용된다.

| 도메인 | 더티 데이터 예시 | 표준화 목표 | 예상 변형 수 |
|--------|--------------|-----------|-----------|
| **공공·행정** | 직업 분류, 주소, 기관명 | KS 표준 코드 | 수십 배 |
| **의료** | 증상명, 약품명, 시술명 | ICD-10, ATC 코드 | 매우 높음 |
| **전자상거래** | 상품명, 브랜드명 | 카테고리 코드 | 수~수십 배 |
| **인사·채용** | 직무명, 기술스택명 | 표준 직무 코드 | 높음 |
| **제조·ERP** | 자재명, 부품 코드 | BOM 표준 코드 | 높음 |
| **금융** | 업종명, 거래 내역 | 업종 분류 코드 | 중간 |

### 5.2 구현 로드맵 (소규모 조직 기준)

```
Week 1-2: 정답지(Ground Truth) 구축
  - 도메인 전문가 + 카탈로그/표준 코드 참조
  - 목표: 표준명 N종 × 주요 변형 3~5개 = 500~1,000개 엔트리
  - 본 연구 정답지 구조(6칼럼) 그대로 사용 가능

Week 3: 기술 스택 설치
  - Ollama 설치 (Windows/Linux/Mac 모두 지원)
  - Python 환경: sentence-transformers, faiss-cpu, rank-bm25
  - 임베딩: dragonkue/BGE-m3-ko (한국어) 또는 paraphrase-multilingual-MiniLM
  - 모델 선택: 하드웨어에 맞게 (VRAM 없으면 CPU 모드)

Week 4: 시범 운영
  - 1,000건 샘플로 정확도 측정
  - Fallback율·에러율 모니터링
  - 취약 유형 파악 → 정답지 보완

Month 2+: 확장 및 자동화
  - 전체 데이터 배치 처리
  - 신규 데이터 입력 시 자동 표준화 파이프라인 연동
  - 주기적 정답지 업데이트 (도메인 변경 대응)
```

### 5.3 기대 효과

| 지표 | 현재 (수작업) | 도입 후 |
|------|-------------|---------|
| 처리 속도 | 3~5일/3,000건 | **30~50분/3,000건** |
| 인력 투입 | 담당자 상시 필요 | 최초 정답지 구축만 |
| 일관성 | 담당자에 따라 편차 | **동일 규칙 100% 적용** |
| 정확도 | 숙련자 ~95%, 신규자 ~70% | **RAG+LLM: 74~88%** |
| 확장성 | 데이터 증가 시 인력 비례 증가 | **데이터량에 무관** |

> **주의**: LLM 정확도 88%는 "88%의 항목은 완벽히 자동화, 나머지 12%는 사람이 검토"를 의미.
> 완전 대체가 아닌 **"자동화 1차 처리 + 불확실 항목 인간 검토"** 하이브리드로 접근하면
> 전체 인력 투입을 90% 이상 줄이면서도 품질을 유지할 수 있다.

### 5.4 한계와 과제

솔직하게 말해야 할 한계도 있다.

**현재 한계:**

1. **정답지 구축 비용**: 처음 정답지(Ground Truth) 만드는 데 도메인 전문가 시간이 필요하다.
   도메인이 바뀌면 정답지도 새로 구축해야 한다.

2. **표준명 외 변형 대응**: 정답지에 없는 완전히 새로운 유형의 더티데이터에 대해 LLM이 할루시네이션을 일으킬 수 있다. Fallback 정책과 신뢰도 임계값 설정이 중요하다.

3. **대형 모델의 GPU 요구**: 최고 성능 모델(gemma4:e4b, VRAM 9.6GB)은 일반 PC 환경에서 실행이 어렵다. 경량 모델(1~3GB)로도 74~78% 정확도는 달성 가능하다.

4. **qwen 계열의 Thinking 토큰 문제**: qwen3.5:9b처럼 Thinking 모드가 활성화된 모델은 같은 VRAM(6.6GB)에서도 0.04개/초로 극단적으로 느려진다. 모델 선택 시 Thinking 모드 유무 확인이 필요하다.

**향후 연구 방향:**

- **Few-shot 정답지 자동 확장**: LLM이 생성한 변형 예시를 정답지에 반영하는 Semi-supervised 접근
- **신뢰도 점수 활용**: LLM 응답에 confidence score를 부여하여 낮은 신뢰도 항목만 인간 검토
- **도메인 어댑터**: 소량의 도메인 데이터로 임베딩 모델을 fine-tuning하여 정확도 추가 향상
- **스트리밍 처리**: 배치가 아닌 실시간 데이터 흐름에서의 표준화 (CDC 방식)

## 6. 결론 및 제언

### 핵심 메시지 3가지

**① 비정형 데이터 정제는 해결 가능한 문제다**

수작업이나 규칙 기반으로는 비용·확장성 모두 한계가 있다.
RAG+LLM은 **도메인 지식(정답지)** 을 주입하여 기계가 의미론적으로 분류하게 한다.
본 연구에서 최고 88.47%의 정확도를 달성했으며, 이는 실무에서 충분히 활용 가능한 수준이다.

**② 로컬 LLM은 보안·비용·안정성에서 클라우드 API의 실질적 대안이다**

단순히 "오픈소스라서 무료"가 아니다.
보안 규정, 반복 처리 비용 구조, 인터넷 독립 운영 필요성이 있는 조직에는
로컬 LLM이 **전략적 선택**이다.

**③ 최적 모델은 하나가 아니다 — 업무 맥락에 맞게 선택해야 한다**

| 상황 | 추천 |
|------|------|
| 정확도가 곧 비용 (의료, 금융) | gemma4:e4b (88.47%) |
| 일반 업무 자동화 | gemma3:4b (84.48%, 속도 균형) |
| 저사양 환경, 파일럿 | exaone3.5:2.4b (74.06%, 1.6GB) |
| Thinking 모델 (qwen/deepseek-r1) | 소규모 데이터 한정 사용 권장 |

### 실무 적용 제언

```
1. "정확도 100%"를 목표로 하지 말 것
   → LLM 88% + 인간 검토 12% 하이브리드가 수작업 100%보다 효율적

2. 정답지 품질이 시스템 품질을 결정한다
   → 500~1,000개의 잘 만든 정답지가 10,000개의 부실한 정답지보다 낫다

3. 첫 도입은 작게 시작하라
   → 전체 데이터의 10%로 파일럿 → 정확도 측정 → 개선 → 확장

4. LLM은 도구이고, 도메인 지식이 핵심이다
   → 같은 LLM도 정답지·프롬프트·카테고리 설계에 따라 55% vs 88%로 갈린다
```
