# RAG 없이 LLM 단독 평가의 필요성

> **작성 기준:** 2026-05-09  
> **관련 연구:** 서울시 공구대여 데이터 공구명 표준화 — RAG v2 Improved  
> **현재 실험 구성:** RAG v1 → RAG v2 → RAG v2 Improved (LLM-only baseline 없음)

---

## 1. 현재 연구의 구조적 공백

지금 실험 설계의 비교 기준점은 다음과 같다.

```
RAG v1  →  RAG v2  →  RAG v2 Improved
                         (현재 최고: 88.5%)
```

**LLM-only baseline이 없다.** 이것은 다음 질문에 답할 수 없다는 뜻이다.

> "RAG가 실제로 얼마나 기여했는가? LLM 자체 지식만으로도 비슷한 성능이 나오지 않는가?"

---

## 2. LLM-only 평가가 필요한 세 가지 핵심 이유

### 2.1 RAG 기여도(contribution)를 수치로 증명할 수 없다

현재 논리 구조:
```
RAG v2 Improved → 88.5%
"RAG 덕분에 좋아진 것이다" ← 이걸 어떻게 증명?
```

비교군이 없으면 이 주장은 주관적 추론이다. 학술적·실무적 보고에서 "RAG 없이는 X%, RAG 있으면 Y%, 즉 RAG가 +Z%pp 기여"라는 구조를 보여줄 수 없다.

### 2.2 LLM 자체 지식의 한계를 정량화하지 못한다

현재 사용 모델들(gemma4:e4b, exaone3.5:7.8b 등)은 한국어 공구 데이터를 사전학습 과정에서 일부 접했을 수 있다. **"기리가 드릴"이라는 사실을 LLM이 이미 알고 있을 가능성**이 있다.

- LLM-only로 70~75%가 나온다면 → RAG의 실질 기여는 +13~18%pp → RAG 구축 비용 정당화 가능
- LLM-only가 60% 이하라면 → RAG가 핵심이었음이 명확해짐

### 2.3 더티데이터 유형별 "LLM 고유 강점 vs RAG 의존 강점" 구분이 불가능하다

일본어 잔재 유형의 성능을 예로 들면:

- **LLM-only 예상**: gemma4:e4b가 훈련 데이터에서 "기리=드릴"을 알고 있다면 RAG 없이도 50~60% 가능
- **RAG 적용 후**: 47.1% — RAG가 오히려 방해했을 수 있음

이 역설적 상황("RAG가 일본어 잔재 유형에서 역효과를 냈을 가능성")을 증명하거나 반박하려면 LLM-only 수치가 반드시 필요하다.

---

## 3. LLM-only 실험 설계

### 3.1 방식 비교

| 방식 | 프롬프트에 포함하는 것 | 측정하는 것 |
|------|------|------|
| **Zero-shot** | 없음. "표준명으로 변환하라"만 | LLM의 순수 세계 지식 |
| **List-constrained** | 전체 표준명 리스트 제공 | 후보 선택 능력 (RAG 없는 oracle retrieval) |
| **Few-shot** | 3~5개 예시 쌍 제공 | 패턴 학습 능력 |

**권장 조합: Zero-shot + List-constrained 두 가지**

- Zero-shot: "LLM이 공구 지식을 얼마나 아는가"
- List-constrained: "검색 없이 리스트만 줘도 되는가" → RAG의 retrieval 단계 기여도를 분리 측정

### 3.2 구조 비교

```python
# 현재 RAG 파이프라인
Input → BGE-m3-ko → BM25+FAISS → k=15 candidates → LLM → 표준명

# LLM-only (zero-shot)
Input → LLM → 표준명
  프롬프트: "다음 공구명을 표준 공구명으로 변환하세요: {input_name}"

# LLM-only (list-constrained)
Input → LLM (전체 표준명 리스트 제공) → 표준명
```

### 3.3 평가 시 주의사항

- 자유 생성(free generation)이므로 LLM이 실존하지 않는 표준명을 생성할 수 있음 (hallucination)
- 평가 방식: exact match 외에 semantic similarity 병행 필요
- 후처리: LLM 출력을 가장 가까운 표준명에 매핑하는 단계 추가 필요

---

## 4. 실험 결과가 어떻게 나오느냐에 따른 논의의 방향

| LLM-only 결과 | 해석 | 시사점 |
|------|------|------|
| ~70%+ | LLM 자체가 이미 강함 | RAG는 정밀도 보완 역할. 경량 모델만으로도 실용화 가능성 논의 |
| ~50~70% | 적당한 LLM 기초 위에 RAG가 핵심 기여 | 현재 연구의 주장을 수치로 뒷받침 |
| ~50% 이하 | LLM 단독으로는 무작위 수준 | RAG의 필수성이 명확. "RAG 없이는 불가능" 결론 |
| 일본어 잔재만 LLM > RAG | RAG가 해당 유형에서 역효과 | 유형별 선택적 RAG 적용 전략 도출 |

---

## 5. 권장 실험 모델 선정 (전체 9개 중 4개)

9개 전수 반복은 과하다. 목적은 대표성이지 전수 비교가 아니다.

| 모델 | RAG 정확도 | 선정 이유 |
|------|:----------:|------|
| **gemma4:e4b** | 88.5% | 필수 — 최고 성능 기준점 |
| **exaone3.5:7.8b** | 79.2% | 필수 — 한국어 특화 LLM. LLM-only 가장 강할 가능성 |
| **gemma3:4b** | 84.5% | 권장 — 2위 모델. LLM-only 강세 여부 확인 |
| **deepseek-r1:1.5b** | 78.4% | 권장 — 최소 사이즈. 소형 모델의 RAG 의존도 하한선 |

**제외 모델 및 이유:**
- gemma4:e2b: e4b 동일 계열, 결과 추론 가능
- deepseek-r1:8b: 1.5b와 8b 중 극단값인 1.5b로 충분
- granite4.1:8b / 3b: 영어 중심 모델. 한국어 공구명 LLM-only는 유의미한 결과 기대 어려움
- exaone3.5:2.4b: 7.8b 결과로 추론 가능

---

## 6. 결론

LLM-only 평가는 선택이 아니라 **연구 완결성의 문제**다. 현재 보고서는 RAG의 효과를 주장하지만 그 근거인 대조군이 없다. 특히 프렉티컴이나 학술 발표 맥락에서 "왜 RAG를 썼나?"라는 질문에 "LLM 단독보다 성능이 X%pp 높기 때문"이라고 수치로 답할 수 없는 것이 현재 연구의 가장 큰 논리적 공백이다.

추가 실험을 한다면 **gemma4:e4b 하나만 골라서** LLM-only zero-shot과 few-shot을 같은 GT 457건으로 평가하는 것이 최소 비용으로 이 공백을 메우는 방법이다.
