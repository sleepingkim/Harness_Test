# 포스터 내용 (국문) — LLM+RAG 기반 비정형 공구 이름 표준화

> 대상: 국내 학술대회 (AI·데이터·정보처리 분야)
> 구성: 초록 / 서론 / 연구 방법 / 실험 결과 / 결론
> 기반: 전문석사 프렉티컴보고서(RAG v1) + RAG v2 개선 실험 결과

---

## 제목

**로컬 LLM과 검색 증강 생성(RAG)을 활용한 비정형 범주형 데이터의 의미론적 표준화**
— 산업용 공구 이름 데이터를 중심으로

*(단축 제목 후보: "오픈소스 LLM·RAG 기반 공구 이름 더티데이터 의미론적 표준화 실험")*

---

## 초록

> *(약 200자 — 포스터 초록란 기준)*

수동 입력으로 생성된 비정형 범주형 데이터는 어휘적 다양성으로 인해 데이터 품질 저하 및 머신러닝 성능 감소를 유발한다. 본 연구는 오픈소스 거대 언어모델(LLM)과 검색 증강 생성(RAG)을 결합한 의미론적 표준화 파이프라인을 제안한다. 서울시 공구대여 데이터(3,352개 고유 공구명, 160종 표준명)를 대상으로 12개 오픈소스 LLM을 두 가지 RAG 구성으로 평가하였다. 기본(Baseline) RAG는 약 55%의 정확도를 보인 반면, 한국어 특화 임베딩(BGE-m3-ko), BM25+FAISS 하이브리드 검색, 후보 확대(k=15), 카테고리 주입을 적용한 개선(Improved) RAG는 최고 **88.47%**의 정확도를 달성하였다(+33.3%p). 또한 기존 연구(RAG v1)의 97.88% 정확도가 데이터 누수에 기인한 과대 추정임을 규명하고 평가 방법론을 개선하였다. 결과적으로, 모델 크기보다 도메인 특화 검색 아키텍처가 성능에 더 큰 영향을 미침을 확인하였다.

**주요어:** 비정형 데이터, 데이터 표준화, 거대 언어모델, 검색 증강 생성, 데이터 품질

## 1. 서론

### 1.1 연구 배경

| 항목 | 수치 |
|------|------|
| 서울시 공구대여 전체 기록 | 11,525건 |
| 고유 공구 이름 문자열 | **3,352개** |
| 실제 공구 표준 종류 | **약 160종** |
| 1종당 평균 표기 변형 수 | **~21가지** |

- 수동 입력 과정에서 동일 공구가 수십 가지 비표준 표현으로 기록됨
- 예: '충전식드릴', '드릴(배터리)', '무선전동드릴(20V)' → 모두 같은 제품

### 1.2 기존 방식의 한계

**규칙 기반(Rule-based) 방식:**
- 정규식, 형태소 분석기 → 구문적(Syntactic) 오류만 처리 가능
- 의미론적(Semantic) 맥락 이해 불가
  - 일본어 잔재: '기리(ぎり)' → '드릴비트' 변환 불가
  - 브랜드·규격 혼입: 'BOSCH 18V 충전드릴세트' → '드릴' 추론 불가
- 3,352개 변형에 수백 개 규칙 필요 → 유지보수 비용 급증

**수작업(Manual):**
- 숙련 작업자 기준 약 3~5일 소요 / 규모 확장 불가

### 1.3 연구 목적 및 기여

1. **평가 방법론 개선** — 검색 지식베이스와 평가 데이터를 완전 분리하여 기존 RAG v1의 데이터 누수 문제 제거
2. **개선된 RAG 파이프라인** — 4가지 기술적 개선(한국어 특화 임베딩, 하이브리드 검색, k값 확대, 카테고리 주입)
3. **오픈소스 LLM 비교 벤치마크** — 12개 모델(1.5B~9B)의 실험적 성능 비교

## 2. 연구 방법

### 2.1 데이터셋

**더티데이터 유형 분류 (5대 분류, 13 세부 유형):**

| 유형 | 예시 | 건수 |
|------|------|------|
| 속성 기입 | '180mm 샌더', '드릴날 세트(콘크리트용)' | 946 |
| 브랜드 혼입 | '보쉬 pushdrive', 'LS 사다리 3단' | 209 |
| 동력원 명시 | '(20)유선 전동드릴', '충전식전동드릴' | 330 |
| 일본어 잔재 | '기리세트', '뺀치', '함마' | 87 |
| 오탈자·인코딩 오류 | '경랑몽키', '렌치센트', '?드럼프' | 117 |
| 세트·복합명사 | '글루건&심', '충전 드라이버/렌치' | 315 |
| 메타데이터·노이즈 | '(1)접톱', '(불가)다카핀' | 147 |

**평가 데이터:**
- 정답지(Ground Truth): 457쌍 수동 구축 — 벡터 DB와 완전 분리
- 벡터 DB: 표준 공구명 160종만 포함 (original→standard 매핑 미포함)

### 2.2 RAG 아키텍처 비교

| 구성 요소 | 기본(Baseline) | 개선(Improved) |
|----------|--------------|--------------|
| 임베딩 모델 | MiniLM-L12 (384차원) | **BGE-m3-ko (1024차원)** ★ |
| 검색 방식 | FAISS만 사용 | **BM25(40%)+FAISS(60%) 하이브리드** ★ |
| 후보 수 (k) | 5 | **15** ★ |
| 프롬프트 | 표준 | **카테고리 정보 주입** ★ |
| 평가 데이터 | 457쌍 (분리) | 457쌍 (분리) |

**하이브리드 검색 점수:**
```
score = 0.4 × BM25_norm + 0.6 × FAISS_cosine_norm
```

**한국어 BM25 토크나이저:** 음절 unigram + bigram
→ '경랑몽키' → ['경', '랑', '몽', '키', '경랑', '랑몽', '몽키']

### 2.3 실험 모델 (12개)

| 계열 | 모델 | 파라미터 |
|------|------|---------|
| Gemma | gemma3:4b, gemma4:e2b, gemma4:e4b | 4B / 2B / 4B |
| Granite | granite4.1:3b, granite4.1:8b | 3B / 8B |
| EXAONE | exaone3.5:2.4b, exaone3.5:7.8b | 2.4B / 7.8B |
| DeepSeek | deepseek-r1:1.5b, deepseek-r1:8b | 1.5B / 8B |
| Qwen | qwen3.5:9b | 9B |

**실험 환경:** NVIDIA RTX 5080 (17.1GB VRAM) | Ollama (로컬 GPU 추론)
| GPU 배치 임베딩 (3,352개 → 약 10초 완료)

### 2.4 평가 지표

| 지표 | 정의 |
|------|------|
| **정확도** | 예측 표준명 vs. 정답 완전 일치율 |
| **Fallback율** | LLM 출력이 후보 밖일 때 top-1으로 강제 대체된 비율 |
| **처리 속도** | 건당 LLM 추론 속도 (건/초) |
| **총 처리 시간** | 3,352건 전체 처리 소요 시간 |

## 3. 실험 결과

### 3.1 모델별 전체 성능

| 순위 | 모델 | 구성 | 정확도 | Fallback | 속도 | 처리시간 |
|:----:|------|------|:------:|:--------:|:----:|:-------:|
| 1 | **gemma4:e4b** | 개선 | **88.47%** | 8.1% | 1.58건/초 | 35분 |
| 2 | gemma3:4b | 개선 | **84.48%** | 6.5% | 1.77건/초 | 32분 |
| 3 | granite4.1:8b | 개선 | **82.48%** | 5.0% | 1.21건/초 | 46분 |
| 4 | gemma4:e2b | 개선 | **80.93%** | 6.4% | 1.93건/초 | 29분 |
| 5 | exaone3.5:7.8b | 개선 | **79.16%** | 9.2% | 1.23건/초 | 46분 |
| 6 | deepseek-r1:1.5b | 개선 | **78.05%** | 85.2% | 1.49건/초 | 37분 |
| 7 | deepseek-r1:8b | 개선 | **77.83%** | 2.6% | 1.40건/초 | 40분 |
| 8 | exaone3.5:2.4b | 개선 | **74.06%** | 13.6% | 1.58건/초 | 35분 |
| 9 | granite4.1:3b | 개선 | **67.85%** | 20.8% | 1.53건/초 | 36분 |
| 10 | deepseek-r1:8b | **기본** | 55.21% | 3.8% | 1.96건/초 | 28분 |
| 11 | granite4.1:8b | **기본** | 55.21% | 14.9% | 1.26건/초 | 44분 |
| 12 | qwen3.5:9b | **기본** | 0.00% | 0.0% | 1.31건/초 | 43분 |

> ⚠ **RAG v1(기존 연구) 주의:** 97.88% 정확도는 정답 쌍을 벡터 DB에 직접 포함한 **데이터 누수** 상태에서 측정된 과대 추정값임. RAG v2는 DB와 평가 데이터를 완전 분리하여 신뢰할 수 있는 평가 수행.

**평균 개선폭:** 기본 36.81% → 개선 79.26% **(+42.45%p)**

### 3.2 주요 발견

**① RAG 환경에서 모델 크기 ≠ 성능**

| 비교 | 결과 |
|------|------|
| gemma3:4b (3.3GB) vs exaone3.5:7.8b (4.8GB) | **84.5% > 79.2%** |
| deepseek-r1:1.5b (1.1GB) vs deepseek-r1:8b (5.2GB) | **78.1% ≒ 77.8%** |

→ 소형 모델도 도메인 특화 RAG로 대형 모델에 필적하는 성능 가능

**② 4가지 개선 요소 각각의 효과**

| 개선 항목 | 대표 효과 |
|----------|---------|
| BGE-m3-ko 임베딩 | 한국어 형태소 유사성 포착 ('경랑몽키' → '몽키렌치') |
| BM25 하이브리드 | 순수 벡터 검색이 놓치는 어휘적 신호 보완 |
| k=15 확대 | granite4.1:8b Fallback율 14.9% → 5.0% |
| 카테고리 주입 | 동의어 공구 간 disambiguation 개선 |

**③ Fallback율 = 명령 이행 능력 지표**
- deepseek-r1:1.5b: 85.2% → 출력 형식 불준수 (JSON 미준수)
- 상위 3개 모델: 5~8% → 실사용 수준

**④ 처리 속도 (v1 vs v2 비교)**

| 항목 | v1 (Mac Mini M1 CPU) | v2 (RTX 5080 GPU) |
|-----|---------------------|-----------------|
| 임베딩 시간 | 수 분 (건당 처리) | **약 10초** (3,352건 일괄) |
| LLM 처리 속도 | 0.06~0.84건/초 (추정) | **1.2~2.0건/초** |
| 전체 처리 시간 | 1~13시간 | **30~50분** |

## 4. 결론

### 4.1 연구 결과 요약

1. **LLM+RAG로 비정형 공구 이름 표준화 가능:** 개선 RAG는 기본 RAG 대비 +33.3%p 향상, 최고 88.47% 달성
2. **도메인 특화 검색 아키텍처가 모델 크기보다 중요:** 소형 모델(3~4GB)이 대형 모델(7.8B)에 필적하거나 초월
3. **데이터 누수 수정으로 신뢰할 수 있는 평가 기준 확립:** 97.88% (v1) → 88.47% (v2)의 의미 차이 규명
4. **로컬 LLM의 실용성 확인:** 개인정보 보호, 외부 API 비용 불필요, 소비자급 GPU(RTX 5080)로 30~50분 처리

### 4.2 연구 한계

- 정답지 커버리지: 457/3,352 = **13.6%** — 전체 더티데이터 분포 대표성 한계
- 17GB 이상 모델: 단일 소비자급 GPU에서 실용 불가 (CPU 오프로드 시 ~0.03건/초)
- deepseek-r1:1.5b: 85.2% Fallback율 → 실사용 적합성 낮음

### 4.3 향후 연구 방향

| 방향 | 내용 |
|------|------|
| ① 대형 모델 실험 | 32B 이상 모델(양자화 적용)의 정확도 검증 |
| ② 정답지 확장 | 전체 3,352건 완전 정답지 구축으로 평가 대표성 강화 |
| ③ Human-in-the-Loop | 저신뢰도 예측에 전문가 검수 통합 (세트·복합명사 유형) |
| ④ 파인튜닝 비교 | LoRA 기반 도메인 파인튜닝 vs. RAG 성능·비용 비교 |
| ⑤ 적용 도메인 확장 | 의료 코드, 상품 SKU, 직무명 등 다른 비정형 범주 데이터 일반화 |
