# 포스터 내용 (한국어) — 공구명 표준화 LLM+RAG 실험

> **파일 성격:** 프렉티컴 독립형 포스터. GT v2 기준 신규 실험 결과만 수록.
> **수록 실험:** RAG v2 파이프라인 12개 모델 + LLM-only Zero-shot 4개 모델
> **작성 기준:** 2026-05-09

## [제목]

서울시 공구대여 데이터 공구명 자동 표준화:
오픈소스 LLM + RAG 파이프라인 실험 결과

## [1] 문제 정의

서울시 공구대여 서비스는 시민에게 자치구별 공구를 대여하는 공공 서비스로, 공구명 입력을 현장 직원의 자유 기입에 맡겨 왔다. 그 결과 3,352개의 공구명 레코드에 약 160종의 표준 공구명만 존재함에도 불구하고, 동일한 공구를 수십 가지 다른 표현으로 기록하는 비표준 표기가 광범위하게 혼재하게 되었다. 예를 들어 '유선전동드릴'은 '전동드릴'로, '기리셋트'는 '드릴비트세트'로, '함마드릴'은 '해머드릴'로 표준화되어야 하지만, 현재 데이터베이스에는 이 모든 표현이 별개의 항목으로 분산되어 있다.

이러한 데이터 품질 문제는 공구 재고 관리, 수요 통계 분석, 검색 서비스의 정확성을 근본적으로 저해한다. 본 연구는 오픈소스 대형 언어 모델(LLM)과 검색 증강 생성(RAG) 파이프라인을 결합하여 이 비표준 공구명을 자동으로 표준명으로 매핑하는 방법론을 제안하고, 12개 모델에 걸친 체계적 실험을 통해 그 실효성을 검증한다.

---

## [2] 더티데이터 유형 분류

비표준 공구명 457건을 전수 분석한 결과, 크게 9개의 유형으로 분류할 수 있었다. 가장 높은 비중을 차지하는 유형은 오탈자로, 전체의 33.9%에 해당하는 155건이다. '경랑몽키', '스판너'처럼 자음·모음의 혼동이나 받침 누락으로 인해 표준 표기와 형태적으로 유사하지만 일치하지 않는 경우가 이에 해당한다.

그 다음으로는 브랜드 혼입(71건, 15.5%), 동력원 명시(50건, 10.9%), 영문·약어 병용(41건, 9.0%), 속성 기입(40건, 8.8%)이 뒤를 잇는다. '보쉬전동드릴'처럼 제조사명이 공구명에 포함되거나, '유선전동드릴'처럼 전원 방식이 명기되거나, 'HSS드릴비트'처럼 규격 약어가 혼용된 경우가 각각의 예시다. '180mm그라인더'처럼 크기 속성이 공구명 앞에 붙는 속성 기입도 빈번하게 관찰되었다. 이 상위 5개 유형이 전체의 78.1%를 차지한다.

나머지 21.9%(100건)는 세트·구성품 표기, 입력 오류성 메타데이터, 일본어 잔재, 특수기호 혼입의 4개 유형으로 구성된다. 특히 일본어 잔재는 '기리(錐)'나 '뺄치(ペンチ)' 같이 한국어와 음운 체계가 전혀 다른 단어가 표준명 대신 사용된 경우로, 자동화 처리에 구조적 어려움을 야기한다.

---

## [3] RAG v2 파이프라인

본 연구의 RAG v2 파이프라인은 임베딩, 하이브리드 검색, 카테고리 주입, LLM 판단, 폴백 처리의 다섯 단계로 구성된다. 임베딩 단계에서는 한국어 임베딩 벤치마크(KURE)에서 1위를 기록한 BGE-m3-ko 모델(1024차원)을 사용하여 공구명을 고차원 벡터로 변환한다. 검색 단계에서는 BM25 음절 바이그램(가중치 40%)과 FAISS 시맨틱 검색(60%)을 결합한 하이브리드 방식으로 k=15개의 후보 표준명을 추출한다. 추출된 후보에는 공구의 대분류·소분류 카테고리 정보를 프롬프트에 함께 주입하여 LLM의 판단 정확도를 높인다. LLM이 후보 목록에 없는 표현을 생성하는 예외적 경우에는 RAG 검색 결과 1위를 자동으로 대체 출력하는 폴백 메커니즘이 작동한다.

기준 버전(baseline)은 MiniLM-L12(384차원) 임베딩과 FAISS 단독 검색, k=5 후보 추출로 구성된다. 동일한 LLM인 granite4.1:8b를 기준으로 비교할 때, 기준 버전은 55.21%의 정확도에 그친 반면 개선 버전(improved)은 82.48%를 달성하여, 임베딩 모델 및 검색 구성의 변경만으로도 약 27pp의 성능 향상이 나타났다.

## [4] 실험 결과

### 4.1 12개 모델 전체 성능

총 9개 모델에 개선된 RAG v2 파이프라인을 적용하고, 3개 모델에 기준 버전을 적용하여 451건의 평가 데이터셋 기준 정확도를 측정하였다. 개선 버전에서 가장 높은 성능을 보인 모델은 gemma4:e4b로, 451건 중 399건을 정확히 표준화하여 88.47%의 정확도를 기록하였다. 이어 gemma3:4b가 84.48%(381건), granite4.1:8b가 82.48%(372건), gemma4:e2b가 80.93%(365건), exaone3.5:7.8b가 79.16%(357건)로 상위 5위를 형성하였다. deepseek-r1:1.5b는 78.05%(352건)로 6위를 기록했으며, 이 모델의 경우 폴백 비율이 85.2%로 매우 높아 LLM 자체의 한국어 생성 능력보다 RAG 검색 결과에 크게 의존하는 양상을 보였다. deepseek-r1:8b는 77.83%(351건), exaone3.5:2.4b는 74.06%(334건), granite4.1:3b는 67.85%(306건)로 뒤를 이었다.

기준 버전으로 테스트한 3개 모델은 모두 현저히 낮은 성능을 보였다. granite4.1:8b와 deepseek-r1:8b baseline이 각각 55.21%(249건)로 공동 10위를 기록하였고, qwen3.5:9b baseline은 에러율 100%로 단 한 건도 표준화하지 못하였다. 이는 기준 버전 파이프라인의 RAG 구성 자체에 해당 모델이 호환되지 않는 문제로, 파이프라인 구성이 모델 선택 못지않게 중요함을 방증한다.

### 4.2 더티데이터 유형별 성능

최고 성능 모델인 gemma4:e4b를 기준으로 유형별 정확도를 분석한 결과, 유형 간 편차가 매우 뚜렷하게 나타났다. 동력원 명시(96.4%), 메타데이터(95.5%), 속성 기입(95.0%), 오탈자(93.8%)는 모두 90% 이상의 높은 정확도를 달성하였다. 특히 전체 더티데이터 중 가장 빈번한 유형인 오탈자(33.9%)에서 93.8%를 기록한 것은 BGE-m3-ko 임베딩이 한국어 형태소 변이를 의미적으로 동일하게 인코딩하는 능력 덕분으로 해석된다. RAG가 없는 LLM-only 조건에서 오탈자의 정확도가 21.9%에 불과했음을 감안하면, RAG의 기여는 +71.9pp에 달한다.

반면 일본어 잔재 유형은 47.1%로 전 유형 중 가장 낮은 성능을 보였다. '기리'와 '드릴비트', '함마'와 '해머'처럼 한국어와 일본어 사이의 음운 단절이 크기 때문에, 시맨틱 임베딩과 BM25 어느 쪽도 이 두 표현을 유사 벡터로 인코딩하지 못한다. LLM-only 조건에서도 19.0%에 머물러, RAG 기여가 +28.0pp로 다른 유형 대비 가장 작았다. 이는 파이프라인 구조적 개선만으로는 해결하기 어려운 지식 공백임을 시사한다.

### 4.3 LLM-only Zero-shot 비교

RAG의 실질적 기여를 정량화하기 위해, 4개 모델에 대해 RAG 없이 LLM만으로 표준화를 수행하는 zero-shot 실험을 병행하였다. 이때 exact_match(표준명과 완전 일치)와 nearest_match(의미상 가장 가까운 표준명으로의 개념적 이해) 두 지표를 함께 측정하였다.

gemma4:e4b의 경우 LLM-only exact_match는 27.4%에 불과하였으나, nearest_match는 63.2%로 나타났다. 이는 모델이 공구의 개념 자체는 이해하지만, 표준 표기로 정확히 수렴하는 능력이 결여되어 있음을 의미한다. RAG를 결합하면 88.5%로 상승하여 +61.1pp의 기여를 확인할 수 있다. 동일한 패턴이 gemma3:4b(LLM-only 23.0% → RAG 84.5%, +61.5pp), exaone3.5:7.8b(9.4% → 79.2%, +69.7pp)에서도 일관되게 관찰되었다. deepseek-r1:1.5b는 한국어 자유 생성 능력 자체가 부재하여 LLM-only 조건에서 0%를 기록하였으나(API 오류가 아닌 언어 한계), RAG 결합 시 78.4%를 달성하였다. 이는 RAG가 단순히 성능을 향상시키는 것을 넘어, LLM의 언어적 한계 자체를 우회할 수 있음을 보여주는 극단적 사례다.

## [5] 핵심 발견

본 실험을 통해 다섯 가지 핵심 발견을 도출하였다.

첫째, RAG는 선택이 아닌 필수다. LLM-only 조건에서 exact_match 정확도는 모델에 따라 9~27% 수준에 머물러 실무 적용이 불가능하지만, RAG를 결합하면 79~88%로 상승하여 +61~70pp의 개선이 일관되게 나타났다. 공공 서비스 데이터 품질 보증 맥락에서는 RAG 없는 LLM 단독 운용을 고려하기 어렵다.

둘째, RAG의 핵심 역할은 표기 앵커링이다. nearest_match(개념 이해) 60~63%와 exact_match(표기 통일) 9~27%의 격차는, LLM이 공구의 의미를 파악하고 있음에도 표준 표기로 정확히 수렴하지 못함을 보여준다. RAG가 제공하는 표준명 후보 풀이 LLM의 출력을 올바른 표기로 유도하는 앵커 역할을 수행한다.

셋째, 임베딩 모델 선택이 파이프라인 성능의 핵심 변수다. BGE-m3-ko로의 교체만으로 동일 LLM 대비 +22~27pp의 성능 향상이 이루어졌다. 특히 전체 더티데이터의 33.9%를 차지하는 오탈자 유형에서 93.8%를 달성한 것은, 해당 임베딩 모델이 한국어 형태소 변이를 의미적으로 동일하게 처리하는 강점에서 비롯된다.

넷째, 일본어 잔재는 현재 파이프라인의 구조적 한계다. '기리'↔'드릴비트', '함마'↔'해머'와 같이 음운 체계가 단절된 대응쌍은 시맨틱 임베딩과 BM25 모두에서 유사 벡터로 인코딩되지 않아, 전 모델에서 47% 이하의 성능에 머물렀다. 동의어 사전 형태의 지식 주입이 현 시점에서 유일한 해결책으로 판단된다.

다섯째, RAG는 언어 생성 능력 자체의 한계도 우회할 수 있다. deepseek-r1:1.5b의 LLM-only 0%→RAG 78.4% 전환은, RAG가 LLM의 언어적 결핍을 구조적으로 보완할 수 있음을 보여주는 사례로, 소형 다국어 모델의 실용적 활용 가능성을 시사한다.

## [6] 개선 방향

현재 파이프라인의 성능 병목을 해소하기 위한 세 가지 개선 방향을 제안한다.

가장 우선순위가 높은 방향은 일본어 동의어 사전의 구축이다. '기리→드릴비트', '함마→해머', '뺄치→펜치', '니빠→니퍼' 등 20~30쌍의 한일 대응 공구 용어를 지식베이스로 사전에 등록하고 RAG 검색 이전 단계에서 치환하면, 현재 47.1%에 머무는 일본어 잔재 유형에서 +30~40pp의 개선이 기대된다. 이는 수작업 비용이 낮으면서 효과가 높은 실용적 개선이다.

두 번째 방향은 BM25 영문 서브워드 처리 보강이다. 현행 음절 바이그램 방식은 'PIPE'와 '파이프'처럼 영문과 한글이 교차 대응되는 경우를 처리하지 못한다. 영문 서브워드 토크나이저를 BM25에 추가 적용하면 영문·약어 유형(현재 82.5%)의 추가적 개선이 가능하다.

세 번째 방향은 인간-참여 검토(Human-in-the-Loop) 큐잉 시스템 도입이다. '기타' 유형(현재 66.7%)처럼 모델 신뢰도가 낮은 케이스를 자동으로 감지하여 전문가 검토 대기열로 분류하면, 전체 파이프라인의 품질 보증 수준을 높일 수 있다. 이는 완전 자동화가 어려운 경계 사례에 대해 운영 비용을 최소화하면서도 정확도를 담보하는 실용적 접근이다.
