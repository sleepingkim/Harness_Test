## TITLE

**Semantic Standardization of Unstructured Categorical Data Using Local LLMs and Retrieval-Augmented Generation: A Case Study on Industrial Tool Names**

*(Short title candidate: "RAG-Based Semantic Standardization of Dirty Tool Name Data with Open-Source LLMs")*

---

## ABSTRACT

> *(~150 words — fits a typical poster abstract box)*

Unstructured categorical data generated by manual entry often contains severe lexical variability, making automated classification unreliable. This study proposes a Retrieval-Augmented Generation (RAG) framework employing open-source Large Language Models (LLMs) to semantically standardize industrial tool names. Using the Seoul Metropolitan Tool Rental Dataset — 3,352 unique dirty tool name strings across 160 standard categories — we evaluate 12 open-source LLMs (1.5B–9B parameters) under two RAG configurations. A baseline RAG (MiniLM-L12 embedding, FAISS top-5 retrieval) achieves ~55% accuracy, while an improved RAG — incorporating a Korean-specialized embedding model (BGE-m3-ko), BM25+FAISS hybrid retrieval, expanded candidate pool (k=15), and category-augmented prompting — reaches up to **88.47%** accuracy (gemma4:e4b), a **+33.3 percentage point** gain. An LLM-only baseline confirms RAG contributes +61 percentage points or more, as LLMs without retrieval achieve only 0–27% exact-match accuracy, demonstrating that RAG is indispensable for practical standardization. Critically, prior inflated results (97.88%) are attributed to train/test data leakage; our evaluation strictly separates retrieval knowledge from ground-truth assessment. Results show that domain-optimized retrieval architecture matters more than model scale for this task.

## 1. INTRODUCTION

### Background
- In data-intensive industries, manually entered categorical fields frequently yield **"dirty data"**: inconsistent, non-standard representations of the same concept.
- Example: the 3,352 unique tool name strings in Seoul's public tool rental database map to only **~160 real tool categories** (~21 variants per category on average).
- Traditional rule-based NLP (regex, morphological analyzers) addresses only **syntactic** errors; it fails on **semantic** variability such as:
  - Japanese-derived legacy terms: *giri* (ぎり) → drill bit
  - Brand/spec attributes embedded in names: *"BOSCH 18V Cordless Drill Set"* → *drill*
  - Compound nouns, abbreviations, typos

### Problem Statement
- Manual standardization of 3,352 records requires ~3–5 expert working days.
- Rule-based automation demands hundreds of hand-crafted rules, with continuous maintenance as new entries arrive.
- **Research question:** Can an open-source LLM, augmented with a small domain-specific knowledge base via RAG, achieve practical accuracy for semantic standardization of unstructured categorical data?

### Contributions
1. **Rigorous evaluation framework** — strict separation of RAG retrieval knowledge base from ground-truth evaluation set, eliminating data leakage present in prior work.
2. **Improved RAG pipeline** — four targeted enhancements (Korean-specialized embedding, hybrid retrieval, candidate pool expansion, category injection).
3. **Comparative benchmark** — 12 open-source LLMs across baseline and improved configurations on a real-world Korean dirty-data corpus.
4. **Dirty data type analysis** — per-type accuracy across 11 dirty data categories, identifying failure mechanisms for each type.
5. **LLM-only vs. RAG quantitative analysis** — zero-shot LLM-only experiment isolating and measuring the precise contribution of RAG retrieval.

### 2.2 RAG Architecture

**Knowledge Base (Retrieval DB):**
- Contains only **160 standard tool names** (no original→standard mapping pairs)
- Ensures zero overlap with the evaluation ground-truth set

**Evaluation Set:**
- 457 curated `(dirty_name → standard_name)` pairs
- **Completely separate** from retrieval knowledge base

### 2.3 Configurations

| Component           | Baseline                                          | Improved                                             |
| ------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| Embedding model     | `paraphrase-multilingual-MiniLM-L12-v2` (384-dim) | `dragonkue/BGE-m3-ko` (1024-dim, Korean KURE #1)     |
| Retrieval           | FAISS (cosine similarity)                         | **BM25 (40%) + FAISS (60%) hybrid**                  |
| Candidate pool (k)  | 5                                                 | **15**                                               |
| Prompt augmentation | —                                                 | **Category injection** (tool category & subcategory) |
| Fallback            | LLM output → top-1 if out-of-candidate            | Same                                                 |

**BM25 Korean tokenizer:** syllable unigram + bigram (e.g., *"경랑몽키"* → ['경', '랑', '몽', '키', '경랑', '랑몽', '몽키']).

**Hybrid score:**
```
score = 0.4 × BM25_norm + 0.6 × FAISS_cosine_norm
```

| Family   | Models                            | Parameters          |
| -------- | --------------------------------- | ------------------- |
| Gemma    | gemma3:4b, gemma4:e2b, gemma4:e4b | 4B / 2B / 4B (edge) |
| Granite  | granite4.1:3b, granite4.1:8b      | 3B / 8B             |
| EXAONE   | exaone3.5:2.4b, exaone3.5:7.8b    | 2.4B / 7.8B         |
| DeepSeek | deepseek-r1:1.5b, deepseek-r1:8b  | 1.5B / 8B           |
| Qwen     | qwen3.5:9b                        | 9B                  |

**Hardware:** NVIDIA RTX 5080 (17.1 GB VRAM), Ollama (local inference), GPU-accelerated batch embedding.

### 2.5 Evaluation Metrics

| Metric               | Definition                                                   |
| -------------------- | ------------------------------------------------------------ |
| **Accuracy**         | Exact match rate: predicted `standard_name` vs. ground-truth |
| **Fallback rate**    | % of LLM outputs outside candidate list → forced to top-1    |
| **Processing speed** | Items/second (LLM inference only)                            |
| **Total LLM time**   | Wall-clock time for 3,352 items                              |

**Why types differ in accuracy — Two-axis framework:**

**Easy types (93–96%)** — *"Modifier removal reveals clear core name"*
- Power source / attributes / metadata: stripping modifier (e.g., "cordless", "18V", "(qty:40)") exposes the standard tool name directly. BGE-m3-ko embeddings map modifier-augmented strings close to the standard name in vector space.
- **Typos (93.8%) — most important finding**: The largest type (33.9% of GT) achieves the highest accuracy among medium-difficulty types. BGE-m3-ko's 1024-dim Korean-specialized embeddings encode morphological variants of the same word as nearby vectors. "경랑몽키" (misspelling) and "경량 몽키렌치" (standard) are embedded closely. This represents the dominant source of the +38 pp improvement over Baseline (MiniLM-L12, ~55%).

**Hard type (47.1%) — Japanese-derived terms: structural failure**

| Failure mechanism | Explanation |
|------------------|-------------|
| Phonological disconnection | `기리` (錐, Japanese: キリ) ↔ `드릴비트`: completely different phoneme sets — low FAISS cosine similarity |
| BM25 n-gram mismatch | Syllable bigrams of `기리` (기,리,기리) share zero overlap with `드릴비트` (드,릴,비,트,드릴,릴비,비트) |
| LLM domain gap | LLM pre-training corpora contain virtually no `기리=drill bit` mapping — cannot select correct candidate even when present |

All 9 models score ≤ 52.9% on this type, confirming it is an **architectural limitation**, not a model selection issue. Solution: explicit Japanese-slang → Korean-standard dictionary injection into the RAG knowledge base.

**Notable cross-model anomaly:**
- *Set/kit items*: exaone3.5:7.8b achieves **96.2%** vs. gemma4:e4b at 84.6% — LG AI's EXAONE appears to have stronger knowledge of Korean industrial synonym pairs (e.g., L-wrench = hex wrench).

### 3.3 LLM-only vs RAG Comparison

To isolate and quantify RAG's contribution, we conducted a zero-shot LLM-only experiment for four models — running the same standardization task without any retrieval augmentation (2026-05-09).

#### LLM-only Zero-shot vs. RAG v2: Comparison Table

| Model | LLM-only Exact | LLM-only Nearest | RAG v2 | RAG Contribution |
|-------|:--------------:|:----------------:|:------:|:----------------:|
| gemma4:e4b | 27.4% | 63.2% | **88.5%** | **+61.1 pp** |
| gemma3:4b | 23.0% | 60.8% | **84.5%** | **+61.5 pp** |
| exaone3.5:7.8b | 9.4% | 60.4% | **79.2%** | **+69.7 pp** |
| deepseek-r1:1.5b | 0% | 0.7% | **78.4%** | **+78.4 pp** |

> **Exact:** output matches ground-truth label exactly. **Nearest:** output is semantically close but does not match the precise standard notation.

#### RAG as Output Anchor

The gap between **Nearest (60–63%) and Exact (9–27%)** in LLM-only results reveals the core mechanism.

- **Nearest ~60%**: The LLM conceptually understands which tool is being referred to.
- **Exact 9–27%**: The LLM cannot reliably reproduce the precise notation from among 160 standard labels.

LLMs understand tool concepts but lack **output standardization discipline**. RAG supplies a bounded candidate list, effectively **anchoring** LLM outputs to one of the 160 standard labels. RAG's primary contribution is therefore not knowledge injection, but **output-space constraint**: it converts an open-ended generation task into a constrained selection task.

This explains why the gap between Nearest and Exact narrows dramatically under RAG — the retrieval mechanism compensates for the LLM's inability to self-impose output format consistency.

#### deepseek-r1:1.5b: RAG Bypasses Language Capability Limit

| Condition | Accuracy |
|-----------|---------|
| LLM-only Exact | **0%** |
| LLM-only Nearest | 0.7% |
| RAG v2 | **78.4%** |

Without RAG, deepseek-r1:1.5b produces essentially zero valid Korean tool name outputs — it cannot freely generate Korean text at this scale (Exact: 0%, Nearest: 0.7%). The model's Korean language generation capability is insufficient for this task in open-ended mode.

However, with RAG, it achieves **78.4%** — surpassing several larger models in the baseline configuration. This demonstrates that RAG does not merely *improve* accuracy; it **circumvents the model's fundamental language limitation** by reframing the problem as candidate selection rather than free generation. A model that cannot write Korean can still *choose* the correct Korean label from a list.

#### Per-Type LLM-only → RAG Improvement (gemma4:e4b)

| Dirty Data Type | LLM-only | RAG v2 | Improvement |
|----------------|:--------:|:------:|:-----------:|
| Power source specified | 8.0% | 96.4% | **+88.4 pp** |
| Typos | 21.9% | 93.8% | **+71.9 pp** |
| Japanese-derived terms | 19.0% | 47.1% | +28.0 pp |

The power source type shows the largest RAG gain (+88.4 pp): LLMs conceptually recognize "cordless drill" but fail to produce the exact standard label "전동드릴" without a candidate list. Once RAG supplies candidates, near-perfect selection follows immediately. Japanese-derived terms remain the most resistant type even with RAG (47.1%), confirming that retrieval knowledge base augmentation (synonym dictionary injection) is needed beyond the current architecture.

### 3.4 Key Findings

**① Model size does not predict performance in RAG settings**
- gemma3:4b (3.3 GB) outperforms exaone3.5:7.8b (4.8 GB): **84.5% vs. 79.2%**
- deepseek-r1:1.5b (1.1 GB) achieves 78.1% — comparable to 8B models with improved RAG
- RAG-supplied domain knowledge compensates for limited model capacity

**② Each improvement component contributes**
- BGE-m3-ko (Korean-specialized, 1024-dim) vs. MiniLM-L12 (multilingual, 384-dim): captures Korean morphological similarity (e.g., *"gyeongrang monkey"* → *monkey wrench*)
- BM25 hybrid: recovers lexical signals missed by pure semantic retrieval
- k=15 expansion: reduces forced fallback (granite4.1:8b: 14.9% → 5.0%)
- Category injection: improves disambiguation between semantically similar classes

**③ Fallback rate as a reliability indicator**
- deepseek-r1:1.5b: 85.2% fallback → model instruction-following failure (output format issues)
- granite4.1:3b: 20.8% fallback → marginal instruction compliance
- Top-3 models: 5–8% fallback — acceptable range for production

**④ Speed vs. accuracy trade-off**

| Scenario | Recommended Model | Accuracy | Speed |
|----------|------------------|---------|-------|
| Accuracy-first | gemma4:e4b | 88.47% | 1.58/s |
| Balanced | gemma3:4b | 84.48% | 1.77/s |
| Speed-first | gemma4:e2b | 80.93% | 1.93/s |

All top models process 3,352 records in **under 50 minutes** on a consumer GPU (RTX 5080).

## 4. CONCLUSION

### Summary
- We present a **RAG-based semantic standardization pipeline** for unstructured categorical dirty data, validated on real-world Korean industrial tool name records.
- Four targeted RAG improvements — Korean-specialized embedding, BM25+FAISS hybrid retrieval, expanded candidate pool (k=15), and category-augmented prompting — collectively raise accuracy from **~55% (baseline) to 88.47% (improved)**.
- A zero-shot **LLM-only experiment** confirms that RAG is not merely helpful but indispensable: LLMs alone achieve only 0–27% exact-match accuracy. RAG contributes **+61 to +78 percentage points** by serving as an output anchor and by enabling models with limited language generation capability to achieve practical performance through candidate selection.
- Smaller models with domain-optimized retrieval achieve competitive or superior accuracy compared to larger models, demonstrating the cost-effectiveness of the proposed approach.
- We identify and correct a **data leakage flaw** in prior RAG evaluation designs, establishing a more rigorous benchmark.

### Limitations
- Ground-truth coverage: 457 / 3,352 = **13.6%** — evaluation set may not fully represent the full dirty-data distribution.
- Models >17B parameters are impractical on a single consumer GPU (RTX 5080, 17.1 GB VRAM) due to CPU offload bottleneck (~0.03 items/s).
- deepseek-r1:1.5b shows high fallback (85.2%), limiting real-world applicability despite moderate accuracy.

### Future Work
1. **Large model evaluation** (32B+) with quantization or multi-GPU inference
2. **Ground-truth expansion** to full 3,352 records for complete coverage
3. **Human-in-the-Loop** integration for low-confidence predictions (ambiguous compound tools, set items)
4. **Domain fine-tuning** comparison: RAG vs. LoRA-adapted models on tool name data
5. **Generalization study** across other dirty categorical domains (medical codes, product SKUs, job titles)
