## 요약

본 보고서는 기존 프렉티컴보고서(RAG v1)의 실험 결과와 방법론을 재검토하고, 개선된 RAG v2 파이프라인의 실험 결과를 제시한다. 핵심 발견은 다음과 같다:

1. **RAG v1의 방법론적 한계**: v1 RAG는 연구자가 구축한 386개 정답 쌍을    벡터 DB에 직접 사용하여 높은 정확도(97%+)를 달성하였으나,    이는 평가 데이터와 검색 컨텍스트 간의 중복(데이터 누수)에 기인한 것으로,    실제 일반화 성능을 과대 추정할 가능성이 높다.

2. **RAG v2의 평가 방법론 개선**: v2는 표준 공구명 160종 목록만을 벡터 DB로 구성하고    정답 쌍 매핑은 평가에만 사용하여 train/test 오염 문제를 근본적으로 제거하였다.

3. **성능 개선 전략 (4가지)**: (i) 한국어 특화 임베딩 모델(BGE-m3-ko) 교체,    (ii) BM25+FAISS 하이브리드 검색, (iii) 후보 k값 확대(5→15),    (iv) 카테고리 정보 프롬프트 주입을 통해 baseline 대비 정확도 향상을 달성하였다.

**현재 실험 완료**: 12개 모델/변형 | 최고 정확도: `gemma4:e4b` (improved) — 88.47%
> 현재까지의 평균 개선폭: baseline 36.81% → improved 79.26% (+42.45%)

## I. 서론

### 1.1 연구 배경

디지털 전환 시대에서 데이터 품질은 기업 운영과 AI 시스템의 신뢰도를 결정하는 핵심 요소이다. 특히 다수의 사용자가 수동 입력하는 비정형 범주형 데이터는 어휘적 다양성, 오탈자, 속성 혼입 등 다양한 형태의 '더티데이터'로 존재한다. 서울시 공구대여 데이터의 공구이름 컬럼은 이러한 문제가 집약된 전형적 사례로, 3,352개 고유 문자열 중 대다수가 비표준적 표현을 포함하고 있다.

이를 해결하기 위해 기존 연구(RAG v1)에서는 대규모 언어모델(LLM)과 검색 증강 생성(RAG) 기법을 결합한 의미론적 표준화 알고리즘을 제안하고 11개 오픈소스 LLM 모델로 실험을 수행하여 최고 97.88%의 정확도를 달성하였다. 그러나 해당 실험의 평가 설계에는 재검토가 필요한 방법론적 문제가 존재하며, 본 보고서는 이를 분석하고 더 엄밀한 평가 체계를 기반으로 한 개선 실험 결과를 제시한다.

### 1.2 연구 목적

본 연구의 세부 목적은 다음과 같다.

**가. 평가 방법론 개선**: train/test 오염이 없는 엄밀한 평가 프레임워크를 구축하여 실제 일반화 성능을 측정한다.

**나. 기술적 개선 검증**: 한국어 특화 임베딩, 하이브리드 검색, 컨텍스트 확장이 표준화 정확도에 미치는 영향을 정량적으로 검증한다.

**다. 처리 효율성 개선**: GPU 가속 임베딩 배치 처리를 통해 대용량 데이터 처리의 실용적 효율성을 확인한다.

## II. 기존 연구(RAG v1) 방법론 재검토

### 2.1 RAG v1 아키텍처 요약

RAG v1 실험(기존 프렉티컴보고서)의 핵심 구성은 다음과 같다:

| 구성 요소 | RAG v1 설정 |
|----------|------------|
| 실행 환경 | Mac Mini M1 (16GB RAM, CPU 전용) |
| LLM 도구 | Ollama 0.6.0 |
| 임베딩 모델 | paraphrase-multilingual-MiniLM-L12-v2 (384차원) |
| 벡터 DB | FAISS IndexFlatL2 |
| **벡터 DB 입력 데이터** | **386개 정답 쌍(original_name → standard_name)** |
| 검색 k값 | 3 |
| 평가 데이터셋 | 386개 정답 쌍 |
| 모델 범위 | 1B~7.8B (11개 모델) |

### 2.2 방법론적 한계: 데이터 누수(Data Leakage) 문제

RAG v1의 가장 중요한 방법론적 문제는 **벡터 DB 구성 데이터와 평가 데이터의 중복**이다.

v1 RAG의 작동 방식:
1. 연구자가 수동 구축한 386개 `(original_name, standard_name)` 쌍을 벡터 DB에 저장
2. 입력 더티데이터를 쿼리로 벡터 DB에서 유사한 `original_name` 항목 3개 검색
3. 검색된 사례의 `standard_name`을 LLM 컨텍스트로 제공
4. 동일한 386개 정답 쌍으로 정확도 평가

**문제**: 평가 항목 자체(또는 그와 매우 유사한 표현)가 벡터 DB 안에 있다. 예를 들어 평가 항목이 '드릴(배터리)'이라면, DB에서 '드릴(배터리) → 드릴' 쌍이 검색 결과 상위에 올라오고, LLM은 사실상 정답이 직접 주어진 상태에서 출력만 하면 된다. 이는 기계학습에서 금기시하는 **train/test contamination**의 전형적 사례이다.

**결과적으로**: RAG v1의 97.88% 정확도는 LLM이나 RAG의 일반화 능력을 반영하는 것이 아니라 "정답이 컨텍스트에 포함된 상태에서 그것을 복사하는 능력"을 측정한 것에 가깝다.

### 2.3 추가적인 방법론 문제점

**의미론적 유사도 측정의 순환성**: v1에서 의미론적 유사도 평가를 위해 RAG에 사용된 동일한 임베딩 모델(MiniLM-L12)을 사용하였다. 이는 RAG 검색 기준과 평가 기준이 동일해지는 순환 평가(circular evaluation)로, 독립적인 품질 지표로서의 의미가 약하다.

**소규모 정답지의 대표성 문제**: 386개 정답 쌍은 3,352개 전체 더티데이터 중 11.5%에 불과하며, 이 중에서도 연구자의 판단에 의해 선별된 데이터이다. 따라서 이 정답지가 전체 더티데이터 분포를 대표한다고 보기 어렵다.

**Few-Shot 단독 모델 사용**: 비교군인 Few-Shot 방식은 Exaone3.5:2.4b 단일 모델만 평가하여, RAG 방식 대비 일반적인 Few-Shot 성능 차이를 단정하기에 근거가 불충분하다.

## III. RAG v2: 개선된 방법론

### 3.1 핵심 설계 원칙

RAG v2는 다음의 설계 원칙을 기반으로 구축하였다:

- **평가 독립성**: 정답 쌍(original→standard 매핑)은 평가에만 사용, 벡터 DB에는 포함하지 않음
- **지식 베이스 분리**: 벡터 DB는 '표준 공구명 160종 목록'만으로 구성 (도메인 지식 역할)
- **진정한 분류 과제**: LLM은 더티데이터만 보고 160종 표준명 중 하나를 선택해야 함
- **재현 가능성**: 모든 파라미터(임베딩 모델, k값, 가중치)를 명시하여 재현 가능하도록 설계

### 3.2 시스템 환경

| 구성 요소 | RAG v2 설정 |
|----------|------------|
| OS | Windows 11 + WSL2 (Ubuntu) |
| GPU | NVIDIA RTX 5080 (VRAM 17.1GB) |
| Python | miniconda3 (3.11) |
| LLM 도구 | Ollama (GPU 100% 사용) |
| 실험 대상 | 3,352개 고유 공구 이름 (전체) |
| 평가 데이터셋 | ground_truth_v2 (457개 정답 쌍) |
| GPU 활용 | 임베딩(sentence-transformers CUDA), LLM(ollama) |

> **참고**: v1(Mac Mini M1 CPU) 대비 LLM 처리 속도가 약 10배 이상 향상됨. 임베딩은 배치 처리(3,352개 일괄)로 수 초 내 완료.

### 3.3 데이터셋

| 항목 | v1 | v2 |
|------|----|----|
| 더티데이터 | 3,352개 (동일) | 3,352개 |
| 정답 쌍 (평가용) | 386개 | **457개** (v2 확장) |
| 벡터 DB 입력 | 386개 original-standard 쌍 | **160개 standard_name 목록만** |
| 표준 공구명 종류 | ~ (명시 없음) | **160종** |

### 3.4 RAG v2 Baseline 아키텍처

```
[입력: 더티 공구명]
      ↓
[임베딩] paraphrase-multilingual-MiniLM-L12-v2 (384차원, GPU)
      ↓
[FAISS 검색] top-5 표준 공구명 후보 (IndexFlatL2)
      ↓
[LLM 프롬프트]
  - 역할: 한국어 공구 이름 분류 전문가
  - 후보 목록 제시 (5개)
  - JSON 출력 요구: standard_name / brand / power_source / specification
      ↓
[Fallback] LLM 출력이 후보 외이면 top-1으로 강제 대체 (비율 측정)
      ↓
[출력: 표준 공구명]
```

**GPU 최적화**: 3,352개 쿼리를 루프 전 일괄 배치 임베딩 → FAISS 전체 탐색 한 번에 완료.
건당 임베딩 호출 제거로 임베딩 시간: 수분 → ~6초.

### 3.5 RAG v2 Improved 아키텍처 (4가지 개선)

| 개선 항목 | 변경 내용 | 이론적 근거 |
|----------|----------|-----------|
| **임베딩 교체** | MiniLM-L12 → `dragonkue/BGE-m3-ko` (1024차원) | 한국어 KURE 리더보드 1위, 공구 도메인 한국어에 최적화 |
| **하이브리드 검색** | FAISS(60%) + BM25(40%) 혼합 | 한국어 공구명은 어절 유사성(BM25)과 의미 유사성(벡터) 모두 중요 |
| **k값 확대** | 5 → 15 | 후보 풀 확대로 정답이 후보에 없는 경우 감소, Fallback율 감소 기대 |
| **카테고리 주입** | 프롬프트에 대분류/소분류 추가 | 동의어 공구(드릴비트 vs 드릴 등) disambiguation에 카테고리 정보 활용 |

**BM25 한국어 토크나이저**: 음절 unigram + bigram 방식으로 한국어 공구명의 부분 문자열 매칭 강화. 예: '경랑몽키' → ['경', '랑', '몽', '키', '경랑', '랑몽', '몽키']

**하이브리드 점수**:
```
score = 0.4 × BM25_norm + 0.6 × FAISS_similarity_norm
```

## V. 정확도 해석: v1 vs v2

### 5.1 수치 비교

| 측면 | RAG v1 | RAG v2 Baseline |
|-----|--------|----------------|
| 최고 정확도 | 97.88% | ~55% (현재 deepseek-r1:8b 기준) |
| 평가 데이터와 DB 중복 | **예** (정답 쌍 직접 사용) | **아니오** |
| 측정 내용 | 근접 쌍 검색 후 복사 능력 | 의미론적 분류 일반화 능력 |
| 평가 엄밀성 | 낮음 (train/test 오염) | **높음** |

### 5.2 수치 차이의 해석

v2의 ~55% 정확도가 v1의 97%+ 대비 낮다는 것은 **모델 능력 저하가 아니라 평가 방법론의 차이**에 기인한다:

- v1은 쿼리와 유사한 '정답 힌트'가 DB에 포함되어 있어, LLM이 컨텍스트를   참조하기만 해도 정답을 도출할 수 있는 구조였다.

- v2는 DB에 표준명 목록만 있어, LLM이 '드릴(배터리)', '충전식전동드릴' 같은   다양한 표현을 '드릴'이라는 표준명으로 **진정하게 추론**해야 한다.

- 55%라는 수치는 '힌트 없이 LLM이 순수하게 맞춘 비율'이며,   이것이 실제 비정형 데이터 정제 시스템의 현실적 성능에 가깝다.

### 5.3 v2 개선 방향의 타당성

v2에서 적용한 4가지 개선(BGE-m3-ko, BM25 하이브리드, k=15, 카테고리 주입)은 각각 명확한 이론적 근거를 가진다:

- **BGE-m3-ko**: 한국어 공구명의 의미론적 유사성 포착 능력 향상   (예: '경랑몽키' ↔ '몽키렌치' 매핑 개선)

- **BM25 하이브리드**: 공구 도메인의 전문 용어는 어휘 수준 매칭이 중요.   벡터 유사성만으로는 놓치는 lexical 신호를 BM25가 보완

- **k=15**: 더 많은 후보 제공으로 정답이 후보 목록에 포함될 확률 증가,   Fallback(강제 top-1 대체) 비율 감소 기대

- **카테고리 주입**: '드릴비트'와 '드릴'은 이름이 유사하지만 용도가 다름.   카테고리('공구' vs '부속품') 정보가 LLM의 disambiguation 능력을 강화
